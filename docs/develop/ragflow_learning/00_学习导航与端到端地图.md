## 2. 系统由哪些运行单元组成

源码开发模式下，最小可用系统通常包括：

```text
浏览器
  │ HTTP / SSE
  ▼
Vite 前端（web/）
  │
  ▼
Quart API（api/ragflow_server.py）
  ├─ MySQL：业务实体、配置、任务事实状态
  ├─ MinIO：原文件、缩略图、Chunk 图片等对象
  ├─ Redis：Stream 队列、锁、取消标记、缓存
  └─ Elasticsearch：Chunk 文本、倒排字段和向量

Task Executor（rag/svr/task_executor.py）
  ├─ 从 Redis 领任务
  ├─ 从 MySQL 读取任务详情
  ├─ 从 MinIO 读取原文件
  ├─ 解析、切片、增强和 Embedding
  ├─ 写 Elasticsearch
  └─ 回写 MySQL 进度
```

API 能正常返回并不代表摄取链路完整；Worker 没启动时，上传仍可能成功，但解析任务不会完成。前端能打开也不代表后端健康；Vite 只是页面开发服务器。

## 3. 三条必须掌握的主链路

### 3.1 文档写入链路

```text
前端选择文件
  → upload_document
  → 校验知识库权限、类型、大小和重名
  → MinIO.put(kb_id, location, blob)
  → 创建 Document
  → 创建 File / File2Document
  → 可选生成缩略图并写 MinIO
  → 返回文档，初始 run=0、chunk_num=0
```

这一阶段只完成“资产登记”，没有生成 Chunk，也没有调用 Embedding。

### 3.2 创建与消费解析任务

```text
POST /api/v1/documents/ingest
  → DocumentService.run
  → queue_tasks / queue_dataflow
  → MySQL 插入 Task
  → Document.run 更新为运行中
  → Redis Stream XADD
  → Task Executor XREADGROUP
  → 按 task_id 从 MySQL 补齐任务上下文
  → TaskManager.run_refactored_task
  → TaskHandler
  → ChunkService.build_chunks
  → Embedding
  → Doc Store insert
  → 更新 Task / Document 进度
  → XACK
```

先写 MySQL、后发 Redis 的设计，使任务详情和进度有持久化落点；Redis 消息只是让 Worker 知道“有任务可取”。

### 3.3 检索与回答链路

```text
问题
  → 鉴权和数据集权限校验
  → 可选问题改写、跨语言和标签提取
  → Query Embedding
  → Dealer.retrieval
       ├─ BM25/全文条件
       ├─ KNN/向量条件
       ├─ 元数据过滤
       ├─ 候选融合
       └─ 可选 Rerank
  → 阈值和分页
  → 组装 Prompt
  → Chat Model 流式生成
  → 引用匹配和返回
```

BM25 与向量召回虽然都由 Elasticsearch 执行，但查询表达式、打分语义和后续融合不是同一种计算。

## 4. 五个核心 ID

| ID | 属于谁 | 主要出现位置 | 用途 |
|---|---|---|---|
| `tenant_id` | 租户/工作空间 | MySQL 多数业务表、ES 索引命名 | 数据与模型配置隔离 |
| `kb_id` | Knowledgebase | Document、ES Chunk、MinIO bucket 参数 | 知识库边界 |
| `doc_id` | Document | Task、File2Document、ES Chunk | 串联文档的全过程 |
| `task_id` | Task | MySQL Task、Redis 消息、日志 | 串联一次分页解析任务 |
| `chunk_id` | 检索文档 | ES `_id`、Task.chunk_ids、图片对象 | 串联文本、向量、页码和派生图片 |

排障时先拿到这些 ID，再查四种存储，效率远高于只按文件名或页面提示搜索。

## 5. 分层阅读方法

每个功能都按以下顺序阅读：

1. 找前端触发点，确认请求 URL、方法和请求体。
2. 找 API 路由，确认鉴权、参数校验和租户来源。
3. 找 Service，确认事务边界与业务状态变化。
4. 找基础设施抽象，如 `STORAGE_IMPL`、`docStoreConn`、`REDIS_CONN`。
5. 找具体实现，如 MinIO、Elasticsearch、Redis Stream。
6. 最后看异常处理、重试、清理与测试。

常用搜索命令：

```bash
rg 'route\("/documents/ingest' api
rg 'def queue_tasks|queue_product' api rag
rg 'class ChunkService|def build_chunks|def insert_chunks' rag
rg 'class Dealer|def retrieval|def search' rag/nlp
rg 'useRunDocument|parseOnCreation' web/src
```

## 6. 建议的动手实验

### 实验 A：追踪一个文件

1. 上传一个只有两页的 PDF，暂不解析。
2. 记录 `kb_id`、`doc_id` 和 MinIO `location`。
3. 在 MySQL 查看 `document` 和 `file2document`。
4. 触发解析，记录所有 `task_id`。
5. 在 Redis Stream 观察 Pending 和确认过程。
6. 在 ES 按 `doc_id` 查询 Chunk，观察文本字段和 `q_*_vec`。

### 实验 B：比较检索方式

准备一个只适合关键词命中的问题和一个只适合语义匹配的问题，分别把 `vector_similarity_weight` 调到接近 `0` 与接近 `1`，比较候选集合、最终得分和引用变化。

### 实验 C：制造可恢复故障

在 Worker 领取任务后、`XACK` 前停止进程，重启后观察 Pending 消息如何被恢复。不要在生产环境做此实验。

## 7. 完成学习的判断标准

当你能独立回答下面问题，就不再只是“会调用 RAGFlow”：

- 为什么文件上传成功后 ES 里仍然没有数据？
- 为什么 Redis 中有消息但 Worker 仍可能查不到任务？
- MinIO 对象与 Document 是通过什么字段关联，而不是通过什么猜测关联？
- ES 为什么能同时保存倒排字段和向量？两种得分在哪里融合？
- `Document.run`、`Task.progress` 和 Redis Pending 各自表达什么状态？
- 一个用户为什么能对应多个 `UserTenant` 记录？
- 删除、取消、重解析或 Worker 崩溃时，四种存储如何恢复一致？
- 升级代码前要备份什么，升级后要验证什么？

## 8. 文档边界

本文档重点解释当前仓库的主路径。RAGFlow 还包括 GraphRAG、RAPTOR、知识编译、连接器、MCP、Sandbox、多种 Doc Store 和 Go 重构路径。学习这些扩展功能时，仍应沿用“入口—状态—存储—恢复—验证”的方法，而不是把每个目录当成孤立模块。
