# 第八册：日志、断点与端到端排障手册

本册给出本机源码模式下可直接执行的排障顺序。目标不是“多打几个断点”，而是先确定故障位于浏览器、API、数据库、队列、Worker、解析器、模型还是 Doc Store。

## 1. 本机启动与日志

当前仓库提供：

```bash
cd /Users/jiangfengtime/WorkSpace/ragflow
./start_local.sh
```

它会启动：

- Colima；
- MySQL、MinIO、Redis、Elasticsearch 容器；
- Quart API；
- Python Task Executor；
- Vite 前端。

默认地址：

```text
前端  http://localhost:9222
API   http://localhost:9380
MinIO http://localhost:9011
MySQL localhost:3307
```

本机脚本日志：

```text
logs/local/api.log
logs/local/task_executor.log
logs/local/frontend.log
```

PID 文件：

```text
.run/local/api.pid
.run/local/task_executor.pid
.run/local/frontend.pid
```

## 2. 第一原则：先定位进程边界

| 现象 | 首先看哪里 |
|---|---|
| 页面打不开 | Vite 进程与 `frontend.log` |
| 页面能开，接口 5xx | API 与 `api.log` |
| 上传成功，解析不动 | Worker、Redis、Task 表 |
| 解析失败 | `task_executor.log`、Task.progress_msg |
| 解析成功，搜索为空 | ES、检索参数、Embedding 配置 |
| 有召回，回答不对 | Rerank、Prompt、Chat 模型和引用 |

不要在 API 进程里等待 Worker 断点。两者是不同进程，必须分别启动 Debug Session。

## 3. 最小健康检查

```bash
curl -fsS http://127.0.0.1:9380/api/v1/system/healthz
curl -fsS http://127.0.0.1:9222 >/dev/null

docker compose \
  -f docker/docker-compose-base.yml \
  -f docker/docker-compose.local.yml \
  ps
```

查看最近日志：

```bash
tail -n 200 logs/local/api.log
tail -n 200 logs/local/task_executor.log
tail -n 100 logs/local/frontend.log
```

实时跟踪：

```bash
tail -F logs/local/api.log logs/local/task_executor.log
```

## 4. 关联 ID 是排障主线

按优先顺序记录：

1. `tenant_id`
2. `kb_id`
3. `doc_id`
4. `task_id`
5. `chunk_id`
6. 查询链路的 `search_id/trace_id`

文件名可能重名，页面文案可能变化，只有这些 ID 能稳定串联数据库、队列、对象存储、索引与日志。

## 5. 已有结构化日志标记

当前代码在三条主链路加入了可搜索的阶段日志。

### 5.1 上传与建 Task

```text
文档存储记录已创建
文档上传完成
文档解析请求已接收
文档任务已创建
文档任务已进入队列
```

示例：

```bash
rg '文档(存储|上传|解析|任务)' logs/local/api.log
rg '<doc_id>' logs/local/api.log
```

### 5.2 Worker

```text
任务已被消费者领取
任务处理流水线已开始
文档切片已生成
向量生成完成
文档切片开始写入检索存储
文档切片已写入检索存储
```

示例：

```bash
rg '任务已被消费者领取|任务处理流水线|文档切片|向量生成' \
  logs/local/task_executor.log
rg '<task_id>|<doc_id>' logs/local/task_executor.log
```

### 5.3 检索

```text
知识库检索已开始
检索候选集已获取
检索候选集排序完成
知识库检索完成
```

这些日志记录 ID、数量、页码和开关，不应记录 API Key、完整问题、文档正文或向量。

### 5.4 六个产品模块

| 模块 | 建议搜索的阶段日志 |
|---|---|
| 知识库 | `知识库已创建`、`知识库配置已更新`、`知识库删除` |
| 聊天 | `聊天应用已创建`、`聊天会话已创建`、`聊天回答`、`RAG上下文已准备完成`、`RAG回答` |
| 搜索 | `搜索应用已创建`、`搜索回答`、`搜索应用召回完成`、`搜索应用引用已构建` |
| 智能体 | `智能体已创建`、`智能体配置已更新`、`智能体回答请求已接收`、`智能体运行`、`智能体组件调试` |
| 记忆 | `记忆库已创建`、`记忆消息写入请求已接收`、`记忆抽取任务`、`记忆消息向量化`、`记忆检索` |
| 文件管理 | `工作区文件`、`工作区文件夹已创建`、`文件关联知识库` |

常用组合：

```bash
# 跟踪一次聊天：先用 session_id，再关联检索和引用日志
rg '<session_id>|聊天回答|RAG(上下文|回答)' logs/local/api.log

# 跟踪一次 Memory 异步抽取：API 和 Worker 两边使用同一 task_id
rg '<task_id>|记忆(抽取任务|消息向量化)' \
  logs/local/api.log logs/local/task_executor.log

# File -> Document 转换是后台线程，HTTP data=true 只表示已调度
rg '文件(与知识库关联已创建|关联知识库)' logs/local/api.log
```

日志级别约定：生命周期边界和状态变化使用 `INFO`，单个关联创建与参数摘要使用
`DEBUG`，可恢复异常使用 `WARNING`，任务或存储失败使用 `ERROR/exception`。高频循环、
token 流和文件正文不记录日志。

## 6. 文件上传链路的断点

建议按层设置，而不是每行单步：

| 顺序 | 位置 | 观察值 |
|---|---|---|
| 1 | 前端上传 Hook | 文件列表、`kb_id`、`parseOnCreation` |
| 2 | `document_api.upload_document` | `current_user.id`、请求文件 |
| 3 | `_upload_local_documents` | 校验结果、失败文件 |
| 4 | `FileService.upload_document` | Document 字典、`location` |
| 5 | `settings.STORAGE_IMPL.put` | bucket=`kb.id`、object=`location` |
| 6 | Document/File2Document 写入 | `doc_id` 和关联 ID |

需要回答的问题：

- 请求是否真正到达 API？
- bucket 和 object key 是什么？
- `Document.id` 在何时生成？
- 原文件存储成功后，哪个数据库写入失败？
- “上传后解析”是否继续发出了 ingest 请求？

## 7. 创建 Task 链路的断点

| 顺序 | 位置 | 观察值 |
|---|---|---|
| 1 | `/documents/ingest` | `run`、`doc_ids`、`delete` |
| 2 | `_run_sync` | 权限校验后的 Document |
| 3 | `DocumentService.run` | 标准任务还是 dataflow |
| 4 | `queue_tasks` | 页数、page_size、Task 数量 |
| 5 | digest 计算后 | 新旧 digest、复用数 |
| 6 | `bulk_insert_into_db` 后 | Task 是否已存在 |
| 7 | `REDIS_CONN.queue_product` | queue、task_id、返回值 |

如果断点停在 API 创建 Task，而 Worker 没停，先确认你是否同时启动了 Worker Debug 进程。

## 8. 消费 Task 的有效断点

不建议把主要断点打在：

```python
msg = redis_msg.get_message()
```

因为 Worker 会持续轮询，每次循环都可能经过附近代码，容易产生“没有任务也一直停”的噪音。

更有效的位置：

1. `collect()` 中确认 `redis_msg is not None` 之后；
2. Task 已从 MySQL 补全之后；
3. `handle_task(task)` 或 `TaskManager.run_refactored_task(task)` 入口；
4. `TaskHandler.handle_task()`；
5. `_run_standard_chunking_impl()`。

可设置条件断点：

```python
task.get("doc_id") == "目标 doc_id"
```

或：

```python
task.get("id") == "目标 task_id"
```

这样不会被其他文档或 Worker 心跳干扰。

## 9. Worker 主链路的断点地图

```text
collect
  → handle_task
  → TaskManager.run_refactored_task
  → TaskHandler.handle_task
  → TaskHandler._init_kb
  → _run_standard_chunking_impl
  → ChunkService.build_chunks
  → embedding
  → ChunkService.insert_chunks
  → settings.docStoreConn.insert
  → progress/statistics/post-processing
  → RedisMsg.ack
```

### `loop.run_in_executor(...)` 后怎么跟

`run_in_executor` 把同步函数交给线程池。IDE 的普通“单步进入”不一定跳进工作线程，应直接在目标 `func` 内设置断点。例如当前是解析函数，就在具体 chunker；当前是 `docStoreConn.insert`，就在 Elasticsearch 实现的 `insert()`。

PyCharm 需要启用多进程/线程调试。命令行参数中的 `--multiprocess` 只解决子进程附加，线程池函数仍应靠目标函数断点捕获。

## 10. 解析与 Chunk 的断点

| 位置 | 核心观察 |
|---|---|
| `TaskHandler._init_kb` | 知识库、tenant、模型和 parser config |
| `ChunkService.build_chunks` | 原始 task、文件 bytes、有效配置 |
| parser factory | 选择了哪个 `rag.app.*` |
| 具体 chunker | 原始 section、页码、布局信息 |
| chunk 标准化 | content、位置、图片、metadata |
| 内容增强 | keyword、question、tag、metadata |
| ID 生成 | `doc_id` 与稳定内容哈希 |

`ctx.recording_context.record(...)` 是执行过程记录，不是 Chunk 持久化。真正把文本和向量写入检索存储的是 `ChunkService.insert_chunks()`，最终落到 `settings.docStoreConn.insert()`。

## 11. Embedding 与索引断点

在 Embedding 后检查：

- 返回数组维度；
- Chunk 数与向量行数是否一致；
- 向量字段名是否为 `q_{dim}_vec`；
- token 统计；
- 空白 Chunk 是否被规范化；
- 知识库实际选择的 Embedding 模型。

在 Bulk 后检查：

```text
response.meta.status == 200
response.body["errors"] == False
len(response.body["items"]) == 预期写入数量
每个 item 不含 error
```

## 12. 查询链路断点

| 顺序 | 位置 | 观察值 |
|---|---|---|
| 1 | `search_datasets` | question、kb_ids、阈值、权重 |
| 2 | `validate_dataset_embedding_models` | 数据集与 Embedding 兼容性 |
| 3 | `cross_languages` | 扩展后的查询文本 |
| 4 | `label_question` | 标签过滤/增强结果 |
| 5 | `Dealer.retrieval` | top_k、page_size、rerank 参数 |
| 6 | `Dealer.search` | filters、MatchTextExpr、MatchDenseExpr |
| 7 | `dataStore.search` | ES 查询体和索引名 |
| 8 | `_knn_scores` / token similarity | 两路分数 |
| 9 | 融合与阈值 | 最终分、淘汰原因 |
| 10 | `rerank_by_model` | 模型分数和顺序变化 |

查询多、断点频繁时，用 `kb_id` 或 `search_id` 做条件断点。

## 13. MySQL 检查

本地 Compose 映射到 `3307`。凭据从本地配置或 `docker/.env` 读取，不要把密码写进文档或 shell history。

```bash
mysql -h 127.0.0.1 -P 3307 -u <user> -p
```

常用只读 SQL：

```sql
SELECT id, kb_id, name, location, run, progress, chunk_num, token_num
FROM document WHERE id = '<doc_id>';

SELECT id, doc_id, from_page, to_page, progress, progress_msg, retry_count
FROM task WHERE doc_id = '<doc_id>' ORDER BY from_page;

SELECT id, name, tenant_id, embd_id, parser_id
FROM knowledgebase WHERE id = '<kb_id>';

SELECT user_id, tenant_id, role, status
FROM user_tenant WHERE user_id = '<user_id>';
```

默认只做 `SELECT`。直接手改 `document.run` 不能恢复 Redis 消息、ES 数据或计数器。

## 14. Redis 检查

先从 Compose 配置确认容器和端口：

```bash
docker compose \
  -f docker/docker-compose-base.yml \
  -f docker/docker-compose.local.yml \
  ps redis
```

进入容器后可查看：

```text
XINFO GROUPS <stream>
XPENDING <stream> <group>
XRANGE <stream> - + COUNT 20
```

不要在运行中的共享环境随意执行 `XDEL`、`XTRIM`、`FLUSHDB` 或手工 `XACK`。先确认消息对应的 MySQL Task 状态。

## 15. MinIO 检查

控制台默认是 `http://localhost:9011`。对上传文档核对：

```text
bucket = kb_id
object = Document.location
thumbnail object = Document.thumbnail 指向的约定位置
```

Document 与对象的关联依赖数据库字段，不是运行时扫描同名文件。缩略图 key 即使可由 `doc_id` 推导，也仍以代码写入和字段记录为准。

## 16. Elasticsearch 检查

本地 ES 端口由 `docker/.env` 的 `ES_PORT` 决定。用户名、密码也从本地配置读取。

先查看索引：

```bash
curl -u '<user>:<password>' http://127.0.0.1:<port>/_cat/indices?v
```

按文档查询 Chunk 时，应使用当前代码实际映射的字段和索引名。不要在命令中粘贴真实生产密码；可用临时环境变量并避免 shell history。

重点核对：

- index 是否属于正确 tenant；
- `kb_id` 与 `doc_id` 是否正确；
- 文本字段是否存在；
- `q_*_vec` 的维度字段是否存在；
- `_id` 是否与 `Task.chunk_ids` 对应；
- Chunk 数与 Document/Task 统计是否一致。

## 17. 常见启动故障

### MySQL `Connection refused`

含义是 API/Worker 已尝试连接，但目标地址没有服务监听。检查：

1. 容器是否运行且健康；
2. 本机源码进程是否应连接 `127.0.0.1:3307`；
3. 是否误用了容器内部主机名 `mysql:3306`；
4. `conf/local.service_conf.yaml` 是否被正确覆盖加载。

### `pyodbc` 缺少 `libodbc.2.dylib`

这是可选数据库连接器导入依赖缺失。若启动继续并且当前不使用 ODBC，可能只是警告；如果对应模块是本次功能必需，再安装 `unixODBC` 并确认动态库路径。不要把这条警告误判为 Task 没消费的唯一原因。

### `pkg_resources` / `SyntaxWarning`

通常是第三方依赖兼容性警告。判断是否致命要看进程是否继续输出 ready、是否退出以及是否有后续 traceback。

## 19. 诊断决策树

```text
请求是否到 API？
  否 → 前端 URL、代理、网络
  是
  ├─ API 是否返回成功？
  │   否 → 鉴权、参数、MySQL、MinIO
  │   是
  ├─ Task 是否存在？
  │   否 → ingest/queue_tasks
  │   是
  ├─ Redis 是否投递/Pending？
  │   否 → queue_product、配置、Redis
  │   是
  ├─ Worker 是否 collect？
  │   否 → 队列名、consumer group、Worker 数量
  │   是
  ├─ Chunk 是否生成？
  │   否 → MinIO、parser、文件格式
  │   是
  ├─ Embedding 是否成功？
  │   否 → 模型配置、API、维度、限流
  │   是
  └─ ES 是否写入并可检索？
      否 → mapping、bulk item、index、filter
      是 → 阈值、融合、rerank、权限
```

## 20. 本册检查点

- 能按进程边界判断应该调 API 还是 Worker。
- 能用 `doc_id/task_id/search_id` 串联日志。
- 能选择不会被空轮询反复命中的条件断点。
- 能判断 Bulk HTTP 200 是否真的全部成功。
- 能只读核对 MySQL、Redis、MinIO 和 ES。
- 能区分可忽略警告与导致进程退出的异常。
