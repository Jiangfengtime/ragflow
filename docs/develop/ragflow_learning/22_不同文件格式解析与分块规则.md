# 第二十二册：不同文件格式解析与分块规则

本册基于当前 Python 源码，重点解释 General 通用策略的格式分支，并补充图片、音频、演示文稿、邮件的独立入口。它不代表 Go 摄取流水线，也不代表所有专用解析策略的行为。完整 Worker 链路见[第二册](./02_文档摄取与深度解析.md)。

## 1. 先区分格式、策略和任务范围

三个概念共同决定实际处理方式：

| 概念 | 来源 | 控制的行为 |
|---|---|---|
| 文件格式 | 文件类型及文件名后缀 | 选择 PDF、DOCX、TXT 等格式处理分支 |
| 解析策略 `parser_id` | 文档配置，通常源自知识库，部分格式自动选择 | 选择 `naive`、`table`、`presentation` 等模块 |
| Task 范围 | Worker 上下文中的 `from_page/to_page` | 限定本次任务处理的页段；不能假定所有格式都使用它 |

`FileService.get_parser()` 对视觉文件选择 picture、音频选择 audio、PPT/PPTX/pages 选择 presentation、MSG/EML 选择 email，其余使用知识库指定策略。后缀路由不等于底层一定支持该格式，例如 pages 需要进一步检查 presentation 的实际支持分支。

General 与 naive 在解析器工厂中指向 `rag/app/naive.py`。PDF 即使使用同一个格式，也可以选择 paper、book 等其他策略，不能套用本册 General 的全部规则。

源码入口：

- `api/db/services/file_service.py::FileService.get_parser`
- `rag/svr/task_executor_refactor/chunk_service.py::ChunkService.build_chunks`
- `rag/app/naive.py::chunk`

## 2. 公共处理链路

```text
Worker 读取完整原文件 binary
  → 根据 parser_id 选择 chunker
  → chunker.chunk(filename, binary, from_page, to_page, parser_config, ...)
  → 格式解析器提取正文/表格/图片
  → 按该分支规则构造 Chunk
  → 添加正文分词、标题、位置等字段
  → Worker 内容增强、生成 Chunk ID、处理图片对象
  → EmbeddingService 生成向量
  → 写入 ES，并更新任务和文档统计
```

`binary` 是完整原文件，不是已经裁好的页段。PDF 页范围另行传给底层解析器，具体执行情况需要看选中的 PDF 实现。`chunk()` 返回内存中的 Chunk 字典，不负责直接写入 ES，也不等于已经生成 Embedding。

General 顶层调用还尝试提取嵌入附件；附件以 `is_root=False` 递归解析，避免再次递归扫描附件。失败会记录错误并继续主文件。开启超链接分析时，部分格式还会抓取链接内容并追加 Chunk，所以最终数量不一定只来自主文档正文。

## 3. 关键配置及实际适用范围

| 配置 | 含义 | 注意事项 |
|---|---|---|
| `layout_recognize` | PDF/部分表格或图片的解析方式 | 与文档级 `parser_id` 不同；可为名称或模型引用 |
| `chunk_token_num` | 文本合并目标 | 不是统一硬上限，默认值取决于具体分支 |
| `delimiter` | 文本拆段分隔符 | 普通字符按分隔规则处理；反引号包裹字符串按整体匹配 |
| `overlapped_percent` | 相邻正文块重叠比例 | 通用合并/Markdown 使用；DOCX 分支不传入该配置 |
| `children_delimiter` | 主块构造后的子块拆分规则 | 在 tokenize 阶段使用，不是任务页范围 |
| `table_context_size` | 表格邻近正文窗口 | DOCX 使用；PDF 当前邻近上下文调用实际读取 image 窗口 |
| `image_context_size` | 图片邻近正文窗口 | 各分支是否使用、怎样使用需要分别看实现 |
| `html4excel` | 将电子表格组织为 HTML | General 电子表格分支会把合并目标设为 0 |
| `analyze_hyperlink` | 抓取超链接内容 | 非所有格式都会提取链接；Markdown 还需要 `hyperlink_urls` |

只有完全不传 `parser_config` 时，`naive.chunk()` 才使用入口定义的整套默认配置。传入部分字典时，各读取位置自行使用缺省值，不能把入口中的 512 当成所有分支的固定默认值。

## 4. 普通文本的实际合并算法

普通合并核心为 `rag/nlp/__init__.py::naive_merge()`。

1. 将输入规范化为 `(文本, 位置)` 列表，并统一换行符。
2. 解析分隔符，对每个 section 拆分，丢弃匹配到的分隔符文本。
3. 为重建正文添加换行，并保留 PDF 位置标记。
4. 按 Token 估计值对相邻段落分组。
5. 重建 Chunk，必要时添加上一块的重叠尾部。

### 4.1 默认 OVER_CAP：软目标

合并判断阈值为：

```text
threshold = chunk_token_num × (100 - overlapped_percent) / 100
```

单段超过 `chunk_token_num` 时独立成块；否则，当已有组的累计大小已经超过 threshold 时，新段开始新块。累计尚未超过时仍追加下一段，即使这次追加造成超出目标。

忽略重建换行带来的小量差异，目标 512、重叠 0、段落大小依次为 200、200、200、100 时：

```text
Chunk 1 = 200 + 200 + 200 = 600
Chunk 2 = 100
```

不会把 600 严格裁成 512 和 88。单段超长也不在此处进行原子切分；后续模型输入长度处理可能截断输入，但不等于修改 ES 中存储的完整 Chunk 正文。

### 4.2 重叠是字符比例

`_compute_overlap_prefix()` 去掉 PDF 位置标记，再按可见字符串长度截取尾部。下一块会无条件加上这段重叠文本，因此最终 Token 数还可能增大。

这里不是精确 Token 重叠，也没有跨 Task 的衔接机制。页段边界处的语义连续性不能仅靠 `overlapped_percent` 保证。

### 4.3 自定义分隔符

当 `delimiter` 含反引号包裹的自定义字符串时，`naive_merge()` 进入独立分段分支：分隔出的每段独立成 Chunk，绕过 Token 合并，不应用普通重叠处理。空分隔符则跳过按分隔符拆段，但不会强制拆开一个超长 section。

## 5. PDF：正文与媒体两路处理

入口：`rag/app/naive.py::chunk` 的 `.pdf` 分支。

```text
layout_recognize → _dispatch_pdf_parser()
  → parser(binary, from_page, to_page, ...)
  → sections（正文及位置） + tables（表格/图片） + pdf_parser
       ├─ tables → tokenize_table() → 独立媒体 Chunk
       └─ sections → naive_merge() → tokenize_chunks() → 正文 Chunk
```

### 5.1 正文

正文进入通用分隔符和 Token 合并规则。`tokenize_chunks()` 可以根据 PDF 位置标记调用 `pdf_parser.crop()` 获取块截图及位置，并去除正文中的位置标记。

因此正文 Chunk 带图片对象或 `img_id` 不代表它一定是图片类内容，可能只是用于定位、展示的正文截图。

### 5.2 表格

`tokenize_table()` 接收 `((img, rows), poss)` 形式的结果。在当前媒体生产者约定中，字符串形式的 rows 表示表格：直接将其构造成一条 `doc_type_kwd="table"` Chunk，保留表格文本、可选图片、页码和坐标。

这里不经过正文 512 Token 合并，也不能理解成固定每 10 行表格生成一块。

### 5.3 图片

同一函数中，列表形式的 rows 表示图像相关文本。默认以 `batch_size=10` 分组连接这些文本项，创建 `doc_type_kwd="image"` Chunk，并带上图片与位置。10 指文本列表项的分组大小，不是图片数量或表格行数的统一规则。

图片是否包含 OCR 或视觉模型描述，由所选 PDF 解析器及模型配置决定；图片二进制本身不直接交给文本 Embedding 模型。

### 5.4 代码与识别失败的媒体

General PDF 分块层没有基于函数、类或 AST 的代码专用规则。代码如果作为 sections 输出，就按正文处理。表格若没有被识别为独立媒体，也可能落入正文路径，结构和检索质量因此不同。

### 5.5 配置例外与排障

- `table_context_size` 或 `image_context_size` 非零会触发上下文补充检查，但当前 PDF 调用实际传入的是 `image_context_size`。仅设置 table 窗口不等于一定添加上下文。
- 部分外部 PDF 解析器在目标非正数时将配置改为 0，避免再合并成更大正文块；这不是跨格式统一的“完整文件一个 Chunk”模式。
- `from_page/to_page` 会传给解析器，但不同实现的范围处理需要分别验证。
- 断点：`_dispatch_pdf_parser()`、解析器返回处、`tokenize_table()`、`naive_merge()`、`tokenize_chunks()`。

## 6. DOCX：独立的图文表格合并

```text
Docx() → sections
  → naive_merge_docx()
  → 可选视觉图片增强
  → doc_tokenize_chunks_with_images()
```

该分支提取正文、表格和图片，利用 `_build_cks()` 构建不同类型单元，给表格和图片添加各自的上下文窗口，再由 `_merge_cks()` 合并。图片下标用于视觉模型增强。

`doc_tokenize_chunks_with_images()` 将上下文与正文拼接，附加图片，区分表格/图片类型；子块拆分只对正文类型应用。

区别：本分支不使用 Task 的 PDF 页范围，也没有将 `overlapped_percent` 传入 DOCX 合并器。不能把普通文本 OVER_CAP 的所有细节直接套到 DOCX。

启用超链接分析时可抓取 DOCX 链接，并在当前分支返回前追加附件和链接结果。

## 7. DOC：Tika 提取文本

`.doc` 分支动态导入 Tika，调用 `tika_parser.from_buffer()` 获取 content，再按换行形成 sections，随后走通用合并和分词。

它不是 DOCX 结构解析：该分支没有同样的独立图片、表格构建过程。Tika 不可用或没有 content 时返回空列表并报告信息；实际运行还需满足 Tika 的服务/依赖条件。

## 8. TXT 与源代码文件

General 支持此分支的后缀：txt、py、js、java、c、cpp、h、php、go、ts、sh、cs、kt、sql。

```text
TxtParser() → 解码/换行规范化/分隔符拆分/OVER_CAP 合并
  → sections → naive_merge() → tokenize_chunks()
```

注意这里有两层处理：TXT 解析器本身已分段合并，之后 General 又进行公共合并，不能只看最终 `naive_merge()` 就忽略解析器前处理。

代码文件按文本处理，没有 AST、函数边界、类边界的统一保证。分隔符设置不当可能切断代码块或丢弃有意义的符号。调试时查看原始文本、TxtParser 输出和最终 Chunk 三层结果。

源码：`deepdoc/parser/txt_parser.py::RAGFlowTxtParser.parser_txt`。

## 9. Markdown：保留段落与图片对应关系

后缀 md、markdown、mdx 进入 `Markdown()`，当前调用参数包括 `separate_tables=False`、`return_section_images=True`。

```text
Markdown 元素解析 → sections/tables/section_images
  → 可选视觉描述追加到 section
  → Markdown 专用合并循环
  → tokenize_chunks[_with_images]()
```

其专用循环在追加下一 section 将超出目标时，通常先封存旧块；短标题例外，尽量与后文合并。它不同于普通正文 OVER_CAP 的“允许追加到超出再关闭”。单个 section 超长仍可能使块超过目标。

重叠按当前文本字符长度截取尾部。有图片时合并图片，并在有重叠时保留旧图片引用。没有视觉模型时跳过图像描述增强，不因此终止文本解析。

Markdown 提取器对围栏代码做保护，避免把代码中的竖线表格误识别为表格；这不等于按代码函数建立专门 Chunk。实际表格保留形式应看 sections/tables 输出，不应假定所有 Markdown 表格都独立成块。

断点：`rag/app/naive.py::Markdown.__call__`、`deepdoc/parser/markdown_parser.py`、`is_markdown` 合并循环。

## 10. CSV、XLS、XLSX：General 与 Table 策略不同

默认调用 `ExcelParser()`，将读取结果组织成 sections，再走普通合并。

- `html4excel=False`：使用普通读取结果。
- `html4excel=True`：调用 `excel_parser.html(binary, 12)`，将表格组织为 HTML 片段，并把 `chunk_token_num` 设为 0；后续仍有公共分隔符处理，不能只凭 0 假定片段绝不会再被拆分。
- `layout_recognize="TCADP Parser"`：调用外部表格解析，区分 CSV/XLSX 文件类型，表格先经 `tokenize_table()`，正文目标设为 0；不可用时报告失败。

这里不是 `parser_id="table"` 的专用列角色/列模式策略。`table_column_mode`、`table_column_roles`、`table_column_names` 的知识库配置合并，应看专用 table 路径，不能推断 General Excel 默认具有相同行为。

## 11. HTML 与 EPUB

HTML：`HtmlParser()` 解码后解析 DOM，移除 style/script、内联 style 和注释，读取块级文本，组织正文块与表格内容。输出转为无坐标 sections，再走通用合并。

它不是浏览器执行网页 JavaScript，也不是网页截图。HTML 中 pre/code 标签不等于启用代码 AST 切分。HTML 表格内容进入 sections 也不保证最终获得 PDF 路径中的 table 类型标记。

EPUB：`EpubParser()` 输出文本段，包装为 `(文本, 空位置)` 后进入通用合并。它不使用 PDF 页码范围，不具有 PDF 坐标语义。

源码：`deepdoc/parser/html_parser.py`、`deepdoc/parser/epub_parser.py`。

## 12. JSON、JSONL、LDJSON

`JsonParser(chunk_token_num)` 先检测文本是否为 JSONL，选择 JSONL 或 JSON 的解析路径，再把结构化数据转换为文本 sections。

JSON 解析器按序列化后的字符长度衡量结构大小，构造函数中的 `max_chunk_size` 会乘 2；因此不能将它直接视为与后续 Token 计数完全相同的 512 Token 硬限制。它有结构拆分及嵌套路径重建逻辑，不是直接对原文件字符串截取固定长度。

输出 sections 之后仍进入 `naive_merge()`，故要区分“JSON 结构拆分”和“通用正文合并”两阶段。若设置分隔符，后处理可能影响完整结构展示，应检查最终正文，不要仅检查中间 JSON 片段。

源码：`deepdoc/parser/json_parser.py::RAGFlowJsonParser`。

## 13. 独立格式策略：图片、音频、演示文稿、邮件

这些文件通常由上传时策略选择进入独立模块，不是 General 的文件后缀分支。

### 13.1 图片及视频：picture

`rag/app/picture.py::chunk` 中，静态图片先尝试配置的 PaddleOCR，缺少结果时使用本地 OCR。OCR 文本较长时直接构建图片 Chunk；较短时尝试租户默认视觉模型描述。视觉模型失败但有 OCR 文本时，可回退到 OCR 文本。

同模块支持的视频后缀进入视频视觉模型调用并构建视频文本 Chunk，而不是同样的静态图像 OCR 流程。支持后缀由代码中的 VIDEO_EXTS 决定。

### 13.2 音频：audio

`rag/app/audio.py::chunk` 将原文件写入临时文件，调用租户默认 ASR 模型转录，对转录结果 tokenize 并返回一条 Chunk，最后清理临时文件。这里没有按 General 的 512 Token 目标再次切分长转录。

### 13.3 演示文稿：presentation

`rag/app/presentation.py::chunk` 的 PPT/PPTX 正常路径通过 `RAGFlowPptParser` 按页提取，逐页构建带页码/位置的 Chunk；失败时尝试 Tika 回退。PDF 选择 presentation 时也有该模块自己的 PDF 路径。

当前 PPT 正常调用将结束参数传为 `MAXIMUM_PAGE_NUMBER`，不能仅凭函数收到 `to_page` 就认为它严格使用了 Task 结束范围。不要用 General 正文 Token 合并规则解释幻灯片分块。

### 13.4 邮件：email

`rag/app/email.py::chunk` 使用邮件解析器读取头部和正文，递归处理 multipart 的 plain/html 内容。纯文本和 HTML 分别解析成 sections，再进行 `naive_merge()`，之后处理附件。

该分支没有把 `overlapped_percent` 传入合并调用；也不能假定每封邮件必定只有一块。MSG/EML 在上传时都可路由到 email，但该入口实际使用 BytesParser，具体 MSG 文件是否兼容应按样本验证，不能把路由选择当成格式支持保证。

## 14. Chunk 生成后：共同字段和存储边界

常见正文包括 `content_with_weight`、`content_ltks`、`content_sm_ltks`；标题分词来自文件名。PDF 或媒体还可能带页码、坐标、图片对象和 `doc_type_kwd`。

后续 Worker 才补充文档/知识库关联、ID、时间、可用状态、增强字段及向量。图片对象另存对象存储，ES 中保留引用；不要把原文件、文档缩略图、正文截图和提取图片视为同一个对象。

文本 Embedding 使用实际编码文本，向量以 `q_<维度>_vec` 字段写入 ES，与正文存储在同一条 Chunk 记录中。完整写入顺序及断点见第二册 Worker 章节。

## 15. 建议的 Debug 检查顺序

1. 查 `document.parser_id/parser_config`，确认是 General 还是独立策略。
2. 查 Task 的页范围，确认当前处理单元而非整文档。
3. 在 `chunker.chunk()` 进入实际模块，核对文件名、binary 和配置。
4. 查看格式解析器输出：sections、tables、图片列表及位置。
5. 查看合并前后每段正文与 Token 估计值。
6. 查看子块拆分、图片引用及字段构建。
7. 到 EmbeddingService 检查最终送给模型的文本，避免把模型截断误认为解析器丢文。
8. 写入 ES 后对照 Chunk ID、正文、类型、位置及向量字段。

建议最小样本包括：跨页 PDF 段落、PDF 图片和表格、无换行长段落、DOCX 图文表格、Markdown 围栏代码/表格、超长 JSON 字段、代码文件、长音频转录。先比较同一配置下的中间输出，再判断参数效果。
