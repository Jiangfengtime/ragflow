# 第二册：文档摄取与深度解析

本册沿一个文档从 HTTP 上传一直追踪到切片写入 Doc Store，是理解 RAGFlow 最重要的一条源码主线。关键方法的分支图和断点路线见[第十九册](./19_知识库文档核心流程图.md)。

## 1. 摄取状态机

```text
上传原文
  -> Document 已创建
  -> 请求 ingest/parse
  -> 创建一个或多个 Task
  -> Task 进入消息队列
  -> Worker 领取任务
  -> 读取原文
  -> 解析与切片
  -> 内容增强
  -> Embedding
  -> 写入 Doc Store
  -> 汇总 Task
  -> 更新 Document 完成状态
```

每个箭头都可能失败。诊断时要先确定停在哪个状态边界。

## 2. 上传入口

REST 入口：

```text
api/apps/restful_apis/document_api.py::upload_document
```

典型步骤：

1. 检查租户是否有数据集访问权限；
2. 校验文件数量、名称、类型和大小；
3. 写入完整文件二进制；PDF 会先尝试可读性检查与修复，不是在这里完成内容解析；
4. 能生成缩略图时另写一个对象；
5. 创建 `Document`，再由 `add_file_from_kb` 建立 `File` 与 `File2Document`；
6. 返回成功文件和逐文件错误。

上传成功只表示原文和元数据已经保存，不代表已经产生 chunk。

`Document.run="0"`、`chunk_num=0` 等初值来自 ORM 默认值。页面勾选“上传后解析”时，前端在上传成功后另发 ingest 请求；未勾选时可以之后点击解析。知识库的 `empty` 分支创建的是空文档记录，不是文件夹；`web` 分支先获取网页并转换后保存，但不应把所有分支都当成 `FileService.upload_document` 的同一实现。分支细节见[第十二册](./12_知识库产品完整链路.md)。

### 解析配置从哪里来

普通本地上传会把 `knowledgebase.parser_config` 写入 `document.parser_config`，可理解为上传时的快照。允许的上传覆盖参数会先做浅层合并，因此不保证两个 JSON 永远相同。更新文档配置也可以改变这份快照。

原文件、缩略图和 Chunk 图片是不同对象：本地知识库上传的原文件是 `(kb.id, document.location)`，缩略图是 `(kb.id, document.thumbnail)`；Chunk 的 `img_id` 在解析阶段生成。文件管理器链接到知识库的文件则应通过 `File2DocumentService.get_storage_address` 查真实地址，不能一律拼 `kb_id + location`。

### 为什么先存原文

异步 Worker 需要在 API 请求结束后独立读取文件；解析失败时也需要原文重试。将原文交给对象存储，使 Worker 不依赖 API 进程的内存或临时目录。

## 3. 解析触发入口

常见入口：

```text
POST /api/v1/documents/ingest
POST /api/v1/datasets/<dataset_id>/documents/parse
```

接口会检查当前运行状态、清理或保留旧任务和旧 chunk，并调用 `DocumentService.run(...)`。

阅读 `DocumentService.run` 时关注：

- 它从 Document 和 Knowledgebase 合并了哪些配置；
- 哪些解析状态不允许重复启动；
- 是否需要删除旧索引；
- 如何计算任务数量和表格编号；
- 任务创建失败后 Document 状态如何处理。

## 4. 任务拆分

`api/db/services/task_service.py` 负责把一个逻辑文档变成物理任务。

拆分依据包括：

- PDF 页范围；
- 大型表格行范围；
- parser 类型；
- 已有任务是否可复用；
- 优先级与队列后缀。

### Task 行、Redis 消息、运行上下文是三种对象

| 对象 | 主要内容 | 数据来源 |
|---|---|---|
| MySQL `task` 行 | `id/doc_id/from_page/to_page/task_type/priority/progress/digest/chunk_ids` 等 | `queue_tasks` 批量插入 |
| Redis 消息 | 当前待处理 Task 的轻量字典，包装在 Stream 的 `message` JSON 中 | `queue_product` |
| Worker 的 `task` 字典 / `ctx` | 任务范围 + 文档位置/配置 + 知识库语言/模型/配置 + 租户模型信息 | `TaskService.get_task` 联表补全，再装配 `TaskContext` |

**`task` 表没有 `parser_config` 字段。** 调试器中 `task["parser_config"]` 来自 `Document.parser_config`，`task["kb_parser_config"]` 来自 `Knowledgebase.parser_config` 的查询别名。

### 页段与完整二进制

PDF 默认每 12 页一个 Task，`paper` 默认 22 页，`task_page_size` 可覆盖；`one`、`knowledge_graph`、开启目录抽取或识别到 MinerU 时使用不拆分页的范围。表格策略按每 3000 行拆分，其他类型通常一个 Task。实际范围仍由对应 parser 的实现消费。

Task 使用 **0-based、右端不包含**的 `[from_page, to_page)`。例如 25 页普通 PDF 通常对应 `[0,12)`、`[12,24)`、`[24,25)`。用户配置 `parser_config.pages` 的结束页也是不包含；源码把起止值各减 1 后生成 Task，不要按闭区间理解。

每个分页 Task 从对象存储取得的仍是**完整文件 bytes**，不是预先裁出的页段；页范围作为单独参数传给 parser。当前拆 Task 不提供跨 Task overlap：同一章节跨页段边界时可能分属两组 Chunk，`overlapped_percent` 也不能自动跨 Task 补齐上下文。需要结合章节结构、任务页数或不拆页策略验证，而不能假定分页绝不损失语境。

### 为什么保留 digest

digest 在写入 Task 之前计算，使用 `DocumentService.get_chunking_config` 的字段及文档 ID、页范围。旧 Task 满足范围/digest 匹配、已完成且存在 `chunk_ids` 时可以复用。

当前 digest 并不覆盖全部运行配置：例如知识库实时表格列角色和 `tenant_embd_id` 不在这份字段集合中，`raptor/graphrag` 还会被排除。因此“页面配置改变”不等于“必然重新执行”。复用与强制删除重解析的边界见[第七册](./07_状态一致性与故障恢复.md)。

## 5. 发布与消费

生产端调用：

```python
REDIS_CONN.queue_product(queue_name, message=task)
```

消费端位于 `rag/svr/task_executor.py`：

```python
REDIS_CONN.queue_consumer(queue_name, group, consumer)
```

消费者组允许多个 Worker 协作处理。任务存在于数据库和消息系统两处：数据库记录长期状态，消息触发实际执行。

`get_unacked_iterator` 先读取**当前 consumer 名下**的 Pending；`next()` 只是推进这个迭代器，不是永远获取全队列第一条。迭代耗尽抛出 `StopIteration` 后，`collect` 再用 `XREADGROUP ... >` 领取新消息。`XACK` 只移除消费组 Pending 记录，不物理删除 Stream 中的消息。失败任务也可能 ACK，不能把 Pending 消失解释为业务成功。

排查队列问题时记录：

1. 生产使用的 queue name；
2. Worker 监听的 task type 和 suffix；
3. consumer group 与 consumer name；
4. 消息是否 pending；
5. 数据库 Task 是否仍被认为 unfinished。

## 6. Worker 主循环

`task_executor.py` 启动时解析 `-i` 与 `-t`，初始化配置、存储、Doc Store 与模型，然后进入异步消费循环。

`collect()` 将 Redis 消息与数据库 Task 合并为执行上下文，并识别普通文档、GraphRAG、RAPTOR、Dataflow、Memory 等任务类型。

不要假设 Worker 只做传统文档切片；同一个执行器已经承载多种后台任务。

## 7. 默认执行路径与解析策略分派

默认 `TE_RUN_MODE=0` 的真实调用链是：

```text
task_executor.handle_task() → collect()
  → TaskManager.run_refactored_task
  → TaskContext(task, limiters, callbacks)
  → TaskHandler.handle_task（异常与取消清理包装）
  → TaskHandler.handle（按 task_type 分派）
  → _bind_embedding_model → _init_kb
  → _run_standard_chunking_impl
```

模型绑定会实际 `encode(["ok"])` 探测维度；`_init_kb(vector_size)` 调用 `docStoreConn.create_idx`，创建/检查当前 tenant 索引和知识库相关 schema，不创建 MySQL 知识库记录。普通任务的 `task_type` 为空串；Memory、Dataflow、GraphRAG 等分支不都执行标准文件解析链。模式选择速查见[第十册](./10_源码索引与数据字典.md#6-te_run_mode)。

当前主路径使用 `rag/svr/task_executor_refactor/chunk_builder.py::get_parser` 映射 `parser_id`，例如：

| parser_id | 主要场景 |
|---|---|
| `general` / `naive` | 均进入 `rag.app.naive`，通用文档 |
| `paper` | 论文结构 |
| `book` | 书籍 |
| `presentation` | 演示文稿 |
| `manual` | 手册 |
| `laws` | 法律文本 |
| `qa` | 问答对 |
| `table` | 结构化表格 |
| `resume` | 简历 |
| `picture` | 图片 |
| `audio` | 音频 |
| `email` | 邮件 |
| `knowledge_graph` | 这里仍映射到 `naive`，图构建是后续独立阶段 |
| `one` / `tag` | 整文切片 / 标签知识库 |

这些是知识组织策略，不是简单的扩展名映射。

## 8. `build_chunks()` 逐段阅读

### 8.1 输入保护

调用方已检查取消并读取原文件。`build_chunks` 用 `ctx.size`（Document 中的大小）检查 `DOC_MAXIMUM_SIZE`，不是重新测量 `len(binary)`；超限时回写失败进度并返回空列表。

### 8.2 读取对象

```text
TaskHandler._run_standard_chunking_impl
  → File2DocumentService.get_storage_address(doc_id)
  -> bucket + object name
settings.STORAGE_IMPL.get(bucket, name)
  -> binary
```

读取发生在 `build_chunks(binary)` **之前**，由 `TaskHandler._get_storage_binary` 完成；实际调用的是对象存储抽象，不要求一定配置 MinIO。

### 8.3 合并解析配置

`merge_table_parser_config_from_kb(ctx.raw_task)` 先浅拷贝 Document 配置；仅 `parser_id=table` 时，使用 `kb_parser_config` 中存在的 `table_column_mode/table_column_roles/table_column_names` 覆盖同名项，其他解析参数不整体改为 KB 配置。

这些知识库字段是在 Worker 加载 Task 时联表取得的，不是每行解析都实时查库；合并结果也不自动回写 Document。这让表格列职责采用知识库级规则（设计意图推断），但也意味着文档的上传覆盖值可能被覆盖。调试时看 `run_chunking` 的合并结果；`chunk_config` 只是记录用字典，而且记录的 `layout_recognizer` 与实际常用字段 `layout_recognize` 不同，不能用它替代有效配置。

### 8.4 调用 chunker

```python
chunker.chunk(
    filename,
    binary=binary,
    from_page=...,
    to_page=...,
    lang=...,
    parser_config=...,
)
```

`run_chunking` 取得 `ctx.chunk_limiter` 后，调用 `thread_pool_exec(chunker.chunk, ...)`。线程池隔离同步阻塞调用，不表示线程能被强制取消，也不保证 Python CPU 工作绕过 GIL；原生解析库的并发能力取决于具体实现。

### 8.5 标准化 chunk

解析器返回的结果会补充：

- `doc_id`、`kb_id` 和可选 PageRank；
- 稳定 chunk ID；
- 创建时间；
- 图片对象 ID；

正文分词和位置通常已由 parser/tokenize 阶段生成，不是 `_prepare_docs_and_upload` 统一重新计算。Chunk ID 为 `xxhash.xxh64(content_with_weight + doc_id).hexdigest()`，随后用作 ES `_id`；同一文档重复正文可能得到相同 ID，不能当作原文位置的唯一标识。

PDF outline 等文档级信息不能简单留在第一块 chunk 中，会被提取并持久化为文档元数据。

### 8.6 返回值和副作用

返回的 `docs` 是内存中的 `list[dict]`，此时**没有 Embedding，也未写普通 Chunk 索引**。但不是完全无副作用：图片可能已写对象存储，大纲/文档元数据可能已写独立检索索引，进度回调及部分 parser 可更新 MySQL。后续失败时应分别核对这些落点。

### 8.7 `record(key, value)` 存在哪里

默认路径注入 `NullRecordingContext`，`record()` 不保存数据。对比模式的 `RecordingContext` 将值保存在当前进程 `_data` 字典，同名键覆盖，列表/字典也不是自动深拷贝；它不直接写日志、MySQL、Redis、MinIO 或 ES。IDE Debug 不会自动把它改成持久化记录，不能依靠 `raw_chunks` 等键充当可靠日志。

## 9. DeepDoc 分层

`rag/app/naive.py::chunk` 根据文件名后缀选择底层解析器，不是统一 MIME 分派：

```text
高层：决定 chunk 的语义边界、标题权重、合并策略
  ↓
格式层：PDF/DOCX/XLSX/HTML/Markdown/Text 等
  ↓
视觉层：OCR、Layout、Table Structure、坐标恢复
```

### PDF 为什么复杂

PDF 更接近“带坐标的绘图指令”而不是语义文档。解析需要解决：

- 字符阅读顺序；
- 多栏布局；
- 页眉页脚；
- 表格单元格；
- 扫描页 OCR；
- 图片与文字关系；
- 标题层级；
- 原文位置回溯。

因此 PDF Parser 同时包含普通文本路径与视觉增强路径。修改 PDF 行为时，要先确认测试文件走的是哪条路径。

### General 的实际分支

| 格式 | 主要行为 | 阅读边界 |
|---|---|---|
| PDF | `layout_recognize` 选解析器，抽 sections/tables，再组织 Chunk | DeepDOC、PlainText、MinerU 等输出与页范围支持不完全相同 |
| DOCX | 自有段落/表格/图片合并，再 tokenize，提前返回 | 不要套用最后公共 `naive_merge` 的 overlap 行为 |
| XLSX/XLS/CSV | General 的 Excel 分支提取文本或 HTML | 不等同于 `parser_id=table` 的列类型/角色建模 |
| TXT/代码 | TxtParser + 公共合并/tokenize | 文件后缀由当前分支正则决定 |
| Markdown | 标题、表格、图片及专用合并 | 短标题会与后文合并，图片描述可调用视觉模型 |
| HTML/EPUB/JSON/DOC | 对应格式解析，再合并 | DOC 分支使用 Tika 等外部依赖 |

`presentation` 是独立高层策略，不要看到底层存在 PPT parser 就认定 General 支持 PPT。内嵌附件和超链接分析也有独立开关/返回分支，应跟踪当前文件实际执行到的路径，而不是只读函数末尾。

## 10. Chunk 边界

通用策略会考虑：

- `chunk_token_num` 目标长度；
- delimiter；
- overlap；
- 标题和章节边界；
- 表格、图片等不可随意切开的结构；
- 页面位置和父子关系。

Chunk 不是越小越好：太小会丢语境，太大则降低召回精度并占用模型上下文。应通过真实问答集合评估，而不是只看平均长度。

### 目标长度不是硬上限

`rag/nlp/__init__.py::naive_merge` 先按 delimiter 切段，再合并段落。默认策略允许超过目标；一个自身超长的段落不会被强制拆到 token 上限。反引号包裹的自定义 delimiter 分支还会绕过 `chunk_token_num`，每个分段直接成为 Chunk。Embedding 阶段的截断则只改变模型输入，不会反向缩短存储正文。

overlap 由规范化后的百分比控制，公共实现取前块尾部字符，不是严格 token 比例，且只作用于本次调用的块。DOCX、Markdown、图片/表格分支有自己的合并方式，不能用一个参数推断所有格式的结果。父子切片另由 `children_delimiter` 产生子片正文和 `mom_with_weight`，不是 Task 页段拆分。

## 11. 内容增强

### 11.1 字段来源、开关和落点

| 内容 | 核心实现 / 开关 | 字段及落点 | 是否调用模型 |
|---|---|---|---|
| 正文分词 | `rag.nlp.tokenize` | `content_with_weight/content_ltks/content_sm_ltks`，普通 Chunk 索引 | 否 |
| 文档名/标题 | 各 parser 构造 doc 模板 | `docnm_kwd/title_tks/title_sm_tks`，普通 Chunk 索引 | 通常否 |
| 页码与位置 | `add_positions`、PDF crop | `page_num_int/position_int/top_int`，普通 Chunk 索引 | 本步骤否；上游 OCR 可用模型 |
| 关键词 | `extract_keywords`，`auto_keywords` 非零 | `important_kwd/important_tks`，普通 Chunk 索引 | 缓存未命中时调用 Chat |
| 问题 | `generate_questions`，`auto_questions` 非零 | `question_kwd/question_tks`，普通 Chunk 索引 | 缓存未命中时调用 Chat |
| 自定义元数据 | `generate_metadata`，启用且配置字段 | 临时 `metadata_obj` 汇总后移除，写文档元数据独立索引 | 可能调用 Chat |
| 内建元数据 | `apply_built_in_metadata`，同一元数据开关 | `file_name/update_time` 等文档元数据 | 字段值直接构造；共享流程仍可能绑定 Chat |
| 标签 | `apply_tags`，KB `tag_kb_ids` 非空 | `TAG_FLD` 指定的标签字段，普通 Chunk 索引 | 匹配已有标签，必要时调用 Chat |
| 图片 | `image2id` | bytes 写对象存储，Chunk 保留 `img_id` | 保存本身不调用模型 |
| 向量 | `EmbeddingService.embed_chunks` | `q_<dim>_vec`，普通 Chunk 索引 | 调用 Embedding |

普通文档元数据位于 `ragflow_doc_meta_<tenant_id>`，与 `ragflow_<tenant_id>` 的 Chunk 索引不同。列表中的 “fields” 是文档元数据字段数，不是 `document` 表的列数，也不是 Chunk 数。人工设置、自动生成、内建规则和表格汇总均可能提供字段。

PDF 位置可回溯真实页坐标；没有 PDF parser 的通用 tokenize 路径可能使用块序号占位，不能把每个 `page_num_int` 都当真实物理页。GraphRAG、RAPTOR、结构图和 Wiki 则是另外的文档/知识库级后处理，见[第十一册](./11_高级RAG与数据流水线.md)。

增强可能调用 LLM，因此摄取速度、成本和失败面会随配置变化。诊断性能时要把“文件解析耗时”和“模型增强耗时”分开统计。

## 12. Embedding

当前核心是 `rag/svr/task_executor_refactor/embedding_service.py::EmbeddingService.embed_chunks`：

1. 为每个 chunk 选择问题文本或正文；
2. 清理表格标签和空白内容；
3. 批量调用 `mdl.encode`；
4. 把标题向量与正文向量按 `filename_embd_weight` 混合；
5. 写入 `q_<vector_size>_vec`。

字段名包含维度，所以更换向量模型可能改变 schema。旧 chunk 与新查询使用不同模型或维度时，不能期待可靠结果，应重新建立索引。

### 12.1 模型调用不是固定某个厂商

```text
Knowledgebase.tenant_embd_id / embd_id
  → _bind_embedding_model → 模型配置解析
  → LLMBundle → TenantLLMService.model_instance
  → EmbeddingModel[llm_factory] 具体适配器
  → encode(texts) → 供应商 SDK / HTTP embeddings API
```

`tenant_embd_id` 优先，解析失败再回退到 `embd_id`，未配置时使用租户默认模型。模型名、供应商、凭据、base URL 的关联见[第一册](./01_运行时配置与数据模型.md)，不是从 `tenant` 表单独读出 API Key。

例如适配器类为 `OpenAI_APIEmbed` 时，其 `encode` 继承 `OpenAIEmbed`，最终 `_call` 调用 `client.embeddings.create`；这代表 OpenAI 兼容协议，不代表模型由 OpenAI 提供。实际使用哪个模型要看适配器对象的 `model_name` 和 `client.base_url`，不要打印 `api_key`。

### 12.2 输入与输出细节

问题增强存在时，Embedding 输入优先使用 `question_kwd`，并非始终编码正文。文件名向量只编码一次，再与各正文/问题向量加权相加，不是拼接。`filename_embd_weight` 默认 0.1；当前 helper 把数值 0 也回退到默认值，不能据此承诺“设 0 完全关闭文件名影响”。

`embed_chunks` 原地修改 `docs`，返回 `(token_count, vector_size)`；返回值不是另一份向量文档。正文先按模型长度截断，适配器还可能再次分批/截断。批大小、并发 semaphore、供应商限流是不同机制。

## 13. 写入 Doc Store

`insert_chunks()` 分批调用：

```text
settings.docStoreConn.insert(
  chunks,
  index_name(tenant_id),
  dataset_id
)
```

写入前需要确保索引存在并具有正确向量维度。失败时会更新进度并尽力处理已写入部分，取消任务也需要清理对应 chunk。

### 13.1 ES Bulk 与 MySQL 检查点

ES 配置下调用 `rag/utils/es_conn.py::ESConnection.insert`：构造 action/source 交替列表，每个 Chunk 的 `id` 同时作为 ES `_id`，正文和 `q_*_vec` 一次写入同一条记录。`ATTEMPT_TIME` 循环是异常重试，不是分别写 BM25 和向量；item 错误会直接返回，不能假定每个失败 item 都重试。

底层 `insert` 成功返回 `[]`，非空列表是错误详情。HTTP 200 还要看 `errors/items`。上层 `ChunkService.insert_chunks` 返回的是布尔结果，不要混淆两个返回约定。

`_insert_main_chunks` 按批成功后累计 ID，到周期检查点或末批才调用 `_update_task_chunk_ids → TaskService.update_chunk_ids` 更新 MySQL；不是先保存 ID 再写 ES，也不是每批都写 MySQL。Task 行本身早在投递时已创建。

主批次使用 `refresh=False`，末尾再尝试调用后端 `refresh_idx`。写入成功、检查点保存、可被搜索、文档 DONE 是四个不同时间点。部分失败、取消和 Task 已删除的竞争边界详见[第七册](./07_状态一致性与故障恢复.md)。

### 最终汇总

各标准 Task 成功后调用 `DocumentService.increment_chunk_num` 累加 Document/Knowledgebase 统计；文档级 Redis 计数器选出最后一个标准 Task 执行收尾。`progress_cb → set_progress → TaskService.update_progress` 写细粒度 Task 进度；API 的进度线程再由 `DocumentService._sync_progress` 汇总 `run/progress/progress_msg/process_duration` 等，不是在这个汇总方法里重新统计全部 ES Chunk/Token。不要用单个 Task 成功推断整个 Document 已完成。

## 14. 解析质量评估

至少从四个层面检查：

| 层面 | 问题 |
|---|---|
| 提取 | 文字、表格、图片是否漏失或乱码 |
| 结构 | 标题、段落、阅读顺序是否正确 |
| 切片 | 边界是否保留完整语义 |
| 可检索性 | 真实问题能否召回对应 chunk |

仅检查页面显示的解析预览，不足以证明检索质量。

## 15. 实验：比较两种切片参数

选择有明确章节结构的文档：

1. 记录默认配置生成的 chunk 数和长度分布；
2. 降低 `chunk_token_num` 并增加 overlap；
3. 重新解析；
4. 用 10 个固定问题做 retrieval test；
5. 比较正确 chunk 的排名、上下文完整性和总 token；
6. 写出哪一种配置更适合该文档类型及原因。
