# 第十八册：知识库文档删除核心方法流程图

本文只画知识库文档删除链路；导入、解析、列表和检索的逐方法图见[第十九册](./19_知识库文档核心流程图.md)，顶部「文件管理」按 File ID 删除的入口见[第十七册](./17_文件管理知识库链接与版本.md#13-删除文件)。流程图使用纯文本，便于在源码仓库和文档站直接阅读。代码入口见[第十二册第 7.2 节](./12_知识库产品完整链路.md#72-删除知识库文档)。

## 1. 方法之间的关系

~~~text
DELETE /datasets/<dataset_id>/documents
  → document_api.delete_documents                  接口校验，传入 Document ID
  → FileService.delete_docs                         逐文档协调清理
      ├─ File2DocumentService.get_storage_address  定位原文件
      ├─ DocumentService.remove_document            删除 Document 与派生数据
      │   ├─ delete_document_and_update_kb_counts   MySQL 文档与 KB 统计
      │   ├─ delete_chunk_images                     MinIO Chunk 图片
      │   ├─ remove_dataset_nav_doc_sync             PageIndex 导航节点
      │   ├─ record_doc_deletion                     结构图延迟清理标记
      │   ├─ remove_wiki_products                    Wiki/Artifacts 来源清理
      │   └─ delete_document_metadata               文档元数据索引
      └─ 删除 File / File2Document / 原文件对象       只在适用时删原文件
~~~

标识不要混淆：API 的 ids 是 Document ID；File ID 只在 File2Document 关联中出现。Chunk ID 用于检索记录和 Chunk 图片对象；原文件地址由 bucket 与 object key 组成。

## 2. document_api.delete_documents

~~~text
解析请求体：ids 或 delete_all
  ├─ 两者都没有 / 同时指定 → 参数错误
  └─ 参数有效
       → 检查调用者能否访问 dataset_id
          ├─ 否 → 权限错误
          └─ 是 → delete_all ?
                    ├─ 是 → 查询该知识库全部 doc_id
                    └─ 否 → 使用请求体中的 doc_id
                 → 校验每个 doc_id 均属于该知识库
                    ├─ 否 → 数据错误
                    └─ 是 → FileService.delete_docs(doc_ids, tenant_id)
                              ├─ 返回错误 → 接口返回错误
                              └─ 无错误 → 返回 deleted 数量
~~~

tenant_id 由登录上下文注入，不是客户端自由指定。入口位于 api/apps/restful_apis/document_api.py。

## 3. FileService.delete_docs

~~~text
get_root_folder → init_knowledgebase_docs
  → 遍历每个 doc_id
      ├─ Document 不存在 / 租户找不到 → 记录错误，处理下一个
      └─ 取得 Document
           → get_storage_address(doc_id) 得到 (bucket, object_key)
           → 删除该 doc_id 的 MySQL Task 行
           → DocumentService.remove_document(doc, tenant_id)
              ├─ 失败 → 记录错误，处理下一个
              └─ 成功 → 查询 File2Document
                         → 仅删除 source_type=KNOWLEDGEBASE 的 File 行
                         → 删除 File2Document 关联
                         → File 行确实被删除？
                            ├─ 是 → STORAGE_IMPL.rm(bucket, object_key)
                            └─ 否 → 保留原文件对象
                         → parser_id=TABLE？
                            └─ 是 → 按知识库 DONE 文档计数并减 1
                                     → 结果 ≤ 0 时清理知识库字段映射
  → 返回逐文档汇总的错误
~~~

init_knowledgebase_docs 只在 .knowledgebase 目录缺失时补建目录及已有文档关联；目录已存在时不会逐条修复缺失关系。Task 的删除在 remove_document 内还会执行一次；但内层的 `cancel_all_task_of()` 同样依赖查询 Task 获得 task_id，外层已删 Task 时通常不能再写入这些任务的取消标记。文档级 counter 会标记 aborted，这不等于运行中 Worker 已停工。字段映射分支当前使用的是 DONE 文档计数（`types=[]`），不能解释成准确统计“剩余 TABLE 文档数”。本方法位于 api/db/services/file_service.py。

## 4. File2DocumentService.get_storage_address

~~~text
输入 doc_id
  → 查 File2Document
     ├─ 找到关联 File，且 source_type 为 LOCAL 或空
     │    → 返回 (file.parent_id, file.location)
     └─ 无关联，或关联的是 KNOWLEDGEBASE 等来源
          → 查 Document
          → 返回 (document.kb_id, document.location)
~~~

该方法只定位对象存储地址，不删除数据，也不通过文件名匹配。位于 api/db/services/file2document_service.py。

## 5. DocumentService.remove_document

~~~text
delete_document_and_update_kb_counts(doc.id)
  ├─ 文档已不存在 → 返回 True，不继续清理
  └─ 删除成功 → 计算租户检索索引名并检查索引/表是否存在
       → cancel_all_task_of：文档 counter 标记 aborted，给仍查得到的 Task 写 Redis 取消标志
       → 再次尝试删除 MySQL Task 行
       → 索引存在？是 → delete_chunk_images
       → 缩略图对象存在？是 → 删除缩略图
       → remove_dataset_nav_doc_sync
       → Doc Store 按 doc_id 删除 Chunk
       → record_doc_deletion
       → 索引存在？是 → remove_wiki_products
       → delete_document_metadata
       → 索引存在？是 → 清理知识图谱中的文档来源引用
       → 返回 True
~~~

除最开始的 Document 行与 KB 计数外，多项清理是“失败记日志并继续”；返回 True 不等于所有外部存储都已清空。索引存在性检查在这些 try/except 之外，检查本身抛错可能发生在 MySQL 已删除之后。文档已不存在时会直接返回，不会再扫残留的外部资源，因此重复调用并不能保证修复一次部分失败。这里不删除 File、File2Document 或原文件。位于 api/db/services/document_service.py。

## 6. delete_document_and_update_kb_counts

~~~text
开启 MySQL 事务
  → 按 doc_id 锁定 Document 行
     ├─ 不存在 → 返回 False
     └─ 存在 → 删除 Document 行
                → Knowledgebase.doc_num 减 1
                → Knowledgebase.chunk_num 减去文档 chunk_num
                → Knowledgebase.token_num 减去文档 token_num
                → 提交事务并返回 True
~~~

这里只保证 MySQL 内的文档删除和知识库计数更新同一事务；ES、Redis、MinIO 不在事务内。

## 7. delete_chunk_images

~~~text
按 doc_id 从 Doc Store 分页查询 Chunk
  → 取本页 Chunk ID
     ├─ 本页为空 → 结束
     └─ 对每个 Chunk ID：MinIO 中存在 kb_id/Chunk ID 对象？
          ├─ 是 → 删除该图片对象
          └─ 否 → 跳过
        → 下一页
~~~

正常写入路径会将 Chunk 的 image 二进制单独写入对象存储，并在检索记录中留下 img_id；此方法删除的是 Chunk 图片，不是 document.thumbnail，也不删除 Chunk 检索记录。调用方仅在索引存在时执行它。

## 8. remove_dataset_nav_doc_sync

~~~text
新建临时 asyncio 事件循环
  → remove_dataset_nav_doc
     → 获取知识库级 Redis 锁
     → 查询该文档的 nav_doc 节点
        ├─ 不存在 → 结束
        └─ 存在 → 删除 nav_doc
                   → 从父 nav_cluster.doc_ids_kwd 移除 doc_id
                   → 父节点仍有文档？
                      ├─ 是 → 更新 doc_count_int
                      └─ 否 → 删除空父节点，并递归清理空祖先
     → 释放锁
  → 关闭临时事件循环
~~~

nav_doc/nav_cluster 是 PageIndex 导航树在 Doc Store 中的派生记录，不是文件管理器的目录，也不是普通 Chunk。位于 rag/advanced_rag/knowlege_compile/dataset_nav.py。

## 9. record_doc_deletion 与下一次结构合并

~~~text
删除文档时：record_doc_deletion
  → 检查知识库检索表是否存在
     ├─ 否 → 结束
     └─ 是 → 必要时补充 deleted_doc_id 字段
               → 插入 doc_deleted 标记，保存 deleted_doc_id

下一次增量结构合并：_cleanup_deleted_docs
  → 读取待处理标记
  → 查找引用已删除文档的知识库级实体/关系
     ├─ 仍有其他来源文档 → 从 doc_ids_kwd 移除已删除 doc_id
     └─ 已无来源文档 → 删除孤立实体/关系
  → 所有结构合并成功后，才消费删除标记
~~~

标记写在 deleted_doc_id 而不是 doc_id 字段，不会被按 doc_id 清理 Chunk 的操作命中。record_doc_deletion 本身不立即删除结构图实体。位于 rag/svr/task_executor_refactor/dataset_structure_merger.py。

## 10. remove_wiki_products

~~~text
检查知识库检索索引是否存在
  ├─ 否 → 结束
  └─ 是 → 删除当前 doc_id 的 Wiki MAP 中间记录
           → 查询 source_doc_ids 包含当前文档的派生产物
              ├─ 仅由当前文档贡献 → 删除该产物
              └─ 还有其他来源 → 只移除当前 doc_id
           → 清理该文档的页面来源跟踪记录
~~~

派生产物包括 Wiki 页面、实体、关系、主题等；共享产物不能因删除一个来源文档就整体删除。位于 api/db/services/document_service.py。

## 11. delete_document_metadata 与知识图谱引用

~~~text
delete_document_metadata
  → 检查独立文档元数据索引 ragflow_doc_meta_<tenant_id>
     ├─ 不存在 / 当前文档无元数据 → 结束
     └─ 存在 → 按文档 ID 删除元数据记录

remove_document 中的知识图谱清理
  → 查找引用该 doc_id 的图谱来源
  → 从共享实体/关系的 source_id 移除 doc_id
  → 标记需重建的 graph，并删除无来源的图谱记录
~~~

文档元数据索引不同于普通 Chunk 索引；知识图谱清理的是来源引用，不是无条件删除整个知识库图谱。

## 12. 调试与失败边界

- 断点顺序：delete_documents → delete_docs → remove_document → delete_document_and_update_kb_counts，再按需要进入图片、导航、结构图和 Wiki 方法。
- 一个 Document 可以有多个 Task；外层和内层重复删 Task，第二次通常影响 0 行。
- 取消是检查点协作，先删 Task 后尝试取消的当前顺序还会丢失 task_id；排查删除期间重新出现的 Chunk 时，需要检查旧 Worker 是否仍写入。TaskService.update_chunk_ids() 的 UPDATE 影响 0 行也不会自动报错。
- 原文件删除由 FileService.delete_docs 控制；从文件管理器链接进知识库的 File 不满足 KNOWLEDGEBASE 条件，因此保留原文件。
- MySQL、Redis、Doc Store、MinIO 没有统一事务。检查异常时按 doc_id 分别核对四种存储，不要只看接口返回值。
