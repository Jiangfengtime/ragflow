# 第十二册：知识库产品完整链路

本册从“知识库”一级菜单出发，串联列表、创建、配置、文档、测试、图谱、知识编译和删除。文档解析细节参见[第二册](./02_文档摄取与深度解析.md)，检索算法参见[第三册](./03_检索问答与引用.md)；导入、解析、文件列表及检索的逐方法流程图见[第十九册](./19_知识库文档核心流程图.md)，删除见[第十八册](./18_知识库文档删除核心方法流程图.md)。

## 1. 页面与路由

前端路由集中在 `web/src/routes.tsx`：

| 页面 | 前端目录 | 作用 |
|---|---|---|
| 知识库列表 | `web/src/pages/datasets/` | 查询、筛选、创建、重命名、删除 |
| 文档列表 | `web/src/pages/dataset/` | 上传、解析、停止、删除、预览 |
| 检索测试 | `web/src/pages/dataset/testing/` | 调整阈值、权重、候选数并查看 Chunk |
| Overview | `web/src/pages/dataset/dataset-overview/` | 数据量、摄取情况和结构概览 |
| Settings | `web/src/pages/dataset/setting/` | Embedding、权限、解析器、Dataflow、标签 |
| Knowledge Graph | `web/src/pages/dataset/knowledge-graph/` | 查看和删除 GraphRAG 图 |
| Compilation | `web/src/pages/dataset/compilation/` | Wiki、Skill、导航和结构产物 |

前端请求主要位于 `web/src/services/knowledge-service.ts`、`web/src/hooks/use-knowledge-request.ts` 和文档上传相关 Hook。

## 2. 数据模型边界

```text
Tenant
  └─ Knowledgebase
       ├─ Document ─< Task
       ├─ Connector2Kb
       ├─ GraphRAG/RAPTOR/Wiki 等 task_id
       └─ Doc Store Chunk(kb_id)

File ─< File2Document >─ Document
```

`Knowledgebase` 保存知识库级默认值：

- `tenant_id`、`created_by`、`permission`；
- `embd_id/tenant_embd_id`；
- `parser_id/pipeline_id/parser_config`；
- `similarity_threshold/vector_similarity_weight`；
- `doc_num/chunk_num/token_num`；
- GraphRAG、RAPTOR、Wiki、Skill 和结构任务标识。

`Document` 会复制创建当时的 parser/pipeline 配置。修改知识库默认设置后，已有 Document 是否同步变化要看具体更新接口，不能仅凭知识库字段推断。

## 4. 创建知识库

```text
dataset-creating-dialog
  → knowledge-service
  → POST /api/v1/datasets
  → create_dataset
  → 校验租户、名称、parser/pipeline 和模型
  → KnowledgebaseService.create_with_name
  → MySQL knowledgebase
  → 返回 dataset_id
```

创建时应关注：

- 同一租户内名称去重；
- `parser_id` 和 `pipeline_id` 的互斥/配合关系；
- Embedding 模型是否已配置；
- `permission=me|team`；
- parser config 是否来自默认值、模板或页面表单。

创建知识库不会立刻创建 ES Chunk。索引通常在首个解析 Task 的 `_init_kb()` 中按 tenant、向量维度和 parser 创建/检查。

## 5. 列表与访问范围

列表接口支持关键字、分页、排序和 owner 过滤。可见性结合：

```text
Knowledgebase.tenant_id
Knowledgebase.permission
UserTenant(user_id, tenant_id, role)
```

页面上的“Owner”不只是展示字段，它决定团队知识库过滤和后续修改权限。读取团队共享知识库和修改/删除他人知识库通常是不同权限等级。

## 6. Settings 的配置分组

### 模型与检索

- Embedding 模型；
- 默认相似度阈值；
- 向量权重；
- PageRank/标签等增强配置。

切换 Embedding 模型涉及向量空间变化。`/embedding/check` 可做兼容性检查，但已有 Chunk 最终仍需重新 Embedding/索引才能完整切换。

### 解析方式

- `parser_id`：内置解析策略；
- `parser_config`：chunk token、overlap、delimiter、layout、metadata 等；
- `pipeline_id`：改走 Dataflow Canvas。

### 数据源

知识库可绑定 Connector。同步过程产生 `SyncLogs`，下载/转换完成后继续复用 Document 和摄取链路。

### 权限

`me` 表示所有者空间，`team` 允许团队成员访问。路由仍需验证调用者确实属于该 tenant。

## 7. 文档列表

知识库详情页把 Document 作为主要资源：

```text
上传 → Document.run=0
解析 → Document.run=1 + Task
完成 → run=3 + chunk/token 统计
失败 → run=4 + progress_msg
停止 → run=2
```

状态值来自 `TaskStatus`，其中还包括 `SCHEDULE=5`；队列、单个 Task 和 Document 汇总进度是不同层。上传只持久化原文件及业务关系，只有独立的 ingest/parse 请求才产生解析任务。停止请求写 Redis 取消标记并更新状态，执行器在检查点响应，接口成功不表示模型、线程池或远端解析服务已物理停工。

常见操作：

- 本地上传；
- 从文件管理链接；
- 修改 parser/config/metadata；
- 批量解析或停止；
- 预览原文和 Chunk；
- 删除文档及索引结果。

### 7.1 查询知识库文件列表

知识库详情页使用 `GET /api/v1/datasets/<dataset_id>/documents`；顶部「文件管理」使用另一套 `/files` 接口。

```text
use-document-request.ts
  → knowledge-service.listDocument
  → document_api.list_docs
  → _get_docs_with_request
  → DocumentService.get_by_kb_id
  → MySQL document + file2document + file
  → DocMetadataService.get_metadata_for_documents
  → 返回 docs / total
```

`list_docs` 先检查知识库权限，再解析分页、排序、文件名、类型、解析状态和元数据等筛选条件。列表主体来自 MySQL；`document.chunk_num/token_num/run/progress` 提供分块数、Token 数和解析进度。这里不查 ES Chunk，也不调用大模型。

- 文档元数据：`DocMetadataService` 从独立的 `ragflow_doc_meta_<tenant_id>` 索引读取 `meta_fields`，供页面展示；元数据筛选先得到匹配的 `doc_id`，再查 MySQL 列表。
- 筛选项统计：请求 `type=filter` 时，改走 `DocumentService.get_filter_by_kb_id`，不返回分页列表。
- 进度刷新：存在运行中的文档时，前端定时重新请求列表。

推荐断点：`list_docs → _get_docs_with_request → DocumentService.get_by_kb_id → DocMetadataService.get_metadata_for_documents`。

### 7.2 删除知识库文档

入口是 `DELETE /api/v1/datasets/<dataset_id>/documents`。`dataset_id` 来自 URL，`tenant_id` 由登录上下文注入；请求体传 `ids`（**Document ID，不是 File ID**），或传 `delete_all=true` 删除该知识库全部文档。

```text
useRemoveDocument
  → knowledge-service.deleteDocument
  → document_api.delete_documents
  → FileService.delete_docs
  → DocumentService.remove_document
  → FileService.delete_docs 收尾
```

按当前代码的执行顺序：

1. `delete_documents` 校验知识库权限、请求参数和每个 `doc_id` 的归属，再把 ID 列表交给 `FileService.delete_docs`。
2. `delete_docs` 调用 `init_knowledgebase_docs`：若 `.knowledgebase` 目录尚不存在，就补建目录及现有文档的 File 关联；随后逐个读取 Document，并通过 `File2DocumentService.get_storage_address(doc_id=...)` 取得原文件的 `(bucket, object_key)`。若关联的是文件管理器中的本地 File，地址来自 `file.parent_id/location`；知识库来源则回退到 `document.kb_id/location`。这里的输入始终是 `doc_id`。
3. 外层先删除该文档的 MySQL Task 行，然后调用 `DocumentService.remove_document`。内层的 `cancel_all_task_of()` 通过查询 Task 找到要写取消标记的 task_id；在这条入口中 Task 已被外层删除，通常没有 task_id 可用，因此不能认为所有运行任务一定收到了取消标记。文档级 pending counter 会被标记 aborted，内层还会再次尝试删 Task。
4. `remove_document` 首先物理删除 MySQL `document` 行，并在同一数据库事务中扣减 Knowledgebase 的 `doc_num/chunk_num/token_num`。随后生成 `ragflow_<tenant_id>` 索引名并检查索引是否存在；这只检查索引或表，不证明当前文档一定有 Chunk。
5. 内层尝试取消后，索引存在时清理 MinIO 中的 Chunk 图片，并单独清理文档缩略图；然后从 PageIndex 导航树移除该文档，再按 `doc_id` 删除检索引擎中的 Chunk。Chunk 记录存 `img_id`，图片二进制单独放在对象存储；缩略图由 `document.thumbnail` 定位。
6. 内层写入 `record_doc_deletion` 标记，供下次结构图增量合并清理孤立实体；同时清理当前文档独占的 Wiki/Artifacts 产物、从共享产物中移除其来源引用，并删除独立元数据索引中的文档元数据、知识图谱引用。PageIndex 导航、结构图和 Wiki 都是派生数据，不是普通文件列表。
7. 回到 `delete_docs`：只删除来源为 `KNOWLEDGEBASE` 的 File 行，再删除 `File2Document` 关联。**只有该 File 行成功删除**，才调用 `STORAGE_IMPL.rm(bucket, object_key)` 删除原文件；从文件管理器链接到知识库的原文件会保留。表格类文档还可能在最后清理知识库字段映射。

这是物理删除，但 MySQL、Redis、检索引擎和对象存储之间没有统一事务。`remove_document` 中部分派生数据清理失败只记录日志并继续；外层按文档汇总显式异常。因此不要仅凭 MySQL 行消失或接口返回成功，就断定所有存储都已清干净。逐方法流程图见[第十八册](./18_知识库文档删除核心方法流程图.md)；顶部「文件管理」按 `file.id` 删除的流程见[第十七册](./17_文件管理知识库链接与版本.md#13-删除文件)。

推荐断点：`delete_documents → FileService.delete_docs → DocumentService.remove_document → DocumentService.delete_document_and_update_kb_counts → settings.docStoreConn.delete / settings.STORAGE_IMPL.rm`。

## 8. 检索测试页

Testing 页面直接调用 dataset search，返回检索结果，不生成最终 Chat 回答；跨语言、关键词、自动元数据过滤和知识图谱增强可能调用 Chat 模型辅助检索：

```text
问题 + 参数
  → /datasets/<id>/search
  → search/search_datasets
  → Dealer.retrieval
  → 返回 chunks、分数、doc_aggs
```

适合用来判断问题出在“召回”还是“回答生成”。如果这里已经没有正确 Chunk，修改 Chat Prompt 通常无效。

## 9. 标签和元数据

知识库支持：

- 标签聚合和重命名；
- 文档 metadata 配置；
- metadata summary；
- flattened metadata；
- 检索前 metadata filter。

元数据过滤先得到允许的 `doc_id` 范围，再作为 Doc Store filter，不属于相关性分数本身。

### 内容增强字段与落库位置

普通文档主链在 `ChunkService.build_chunks()` 中完成内容增强，再交给 Embedding 与插入。分词、标题和位置通常由解析器提供，关键词、问题、标签与文档元数据按配置启用，不能把它们都理解为默认开启的 LLM 步骤。

| 增强信息 | 字段或结果 | 来源/条件 | 持久化位置 |
|---|---|---|---|
| 正文与细粒度分词 | `content_ltks/content_sm_ltks` | 解析器、tokenizer | 普通 Chunk 索引 |
| 标题与标题分词 | `docnm_kwd/title_tks/title_sm_tks` | 解析器按格式生成 | 普通 Chunk 索引 |
| 关键词 | `important_kwd/important_tks` | `auto_keywords` 开启，缓存或 Chat 抽取 | 普通 Chunk 索引 |
| 问题 | `question_kwd/question_tks` | `auto_questions` 开启，缓存或 Chat 生成 | 普通 Chunk 索引；也可能成为 Embedding 输入 |
| 文档元数据 | `meta_fields` | `enable_metadata` 且配置 `metadata/built_in_metadata`；也可手工更新 | 独立 `ragflow_doc_meta_<tenant_id>` 索引 |
| 页码与位置 | `page_num_int/position_int/top_int` | 解析器确实有可用位置时 | 普通 Chunk 索引，用于引用定位 |
| 标签与 PageRank | `tag_feas/pagerank_fea` | 标签知识库或相应权重配置 | 普通 Chunk 索引 |
| 图片与大纲 | `img_id`、文档 `outline` | 格式/解析器支持 | 图片在对象存储，outline 在独立元数据索引 |

`metadata_obj` 是每个 Chunk 的临时抽取结果，汇总到文档后删除，再交给 `DocMetadataService.update_document_metadata()`；它不是随 Chunk 写入的最终元数据字段。PDF 大纲和表格专用字段处理还有各自路径，未必受自动元数据开关控制。位置字段也不是每种格式都存在，不能只凭缺少 `page_num_int` 断言解析失败。

配置来源要顺着 `KB parser_config → Document parser_config → TaskContext` 检查。`ingest(apply_kb=true)` 当前只同步 `llm_id/enable_metadata/metadata` 等选定字段，不会无条件覆盖全部解析配置。字段生成代码见 `chunk_post_processor.py`，向量输入规则见 `embedding_service.py`，字段更完整的链路见[第二册](./02_文档摄取与深度解析.md)。

## 10. GraphRAG、RAPTOR 与 Compilation

这些能力不是创建知识库后自动全部存在：

- GraphRAG 需要单独构建实体关系；
- RAPTOR 需要构建层级摘要；
- Wiki/Skill/Navigation/Structure 使用特殊 Task 和 `compile_kwd`；
- Knowledgebase 保存相应 task_id 和完成时间。

GraphRAG 的 `task_type=graphrag` 与 Compilation 的 `structure_graph` 也应分开读：当前 `/datasets/<id>/index` 的 `index_type=graph` 映射为 `structure_graph`，由结构图合并器处理；`index_type`、KB 的 task_id 字段名称和 Worker task_type 不是始终一一同名。沿 `_INDEX_TYPE_TO_TASK_TYPE → TaskHandler.handle` 确认实际分支。

具体参见[第十一册](./11_高级RAG与数据流水线.md)。

## 11. 删除知识库

实际入口是 `dataset_api.delete → dataset_api_service.delete_datasets → _delete_datasets_sync`，删除权限要求知识库 `tenant_id` 等于调用租户，比团队共享读取严格。当前顺序是：

1. 将排队/运行中的 `SyncLogs` 标为 CANCEL，阻止尚未开始的同步继续领取。
2. 逐 Document 调用 `remove_document()`，清理文档、计数、普通 Chunk 和已实现的派生数据；删除知识库来源的 File 行和 File2Document。
3. 删除知识库来源的目录节点，调用 `docStoreConn.delete_idx(index_name, kb_id)`，然后删 Knowledgebase。
4. 删除 Connector2Kb、SyncLogs，最后扫掉循环期间未覆盖的残留 Document 行。

`delete_idx` 的清理粒度要看后端实现，不能把 tenant 索引名直接等同于“删除整个租户数据”。这条入口没有像 `FileService.delete_docs()` 那样逐个删除原文件对象，也未在此统一清理 Chat/Search 的知识库引用、特殊任务和版本历史。正在执行的 Connector 同步不能靠更新 SyncLogs 立即中断，最后残留 Document 扫描也不是完整外部存储清理。

跨 MySQL、Redis、Doc Store 和对象存储没有统一事务；应同时检查 `success_count/errors` 和残留资源，不能把上面的边界补成代码尚未实现的清理能力。
