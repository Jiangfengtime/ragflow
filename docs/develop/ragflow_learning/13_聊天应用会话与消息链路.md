# 第十三册：聊天应用、会话与消息链路

“聊天”一级菜单管理的是可配置 RAG 应用，不只是一次模型请求。核心对象是 `Dialog`、`Conversation` 和知识库检索链路。

## 1. 三个对象不要混淆

| 对象 | 表 | 生命周期 |
|---|---|---|
| Chat/Dialog | `dialog` | 一个聊天应用的长期配置 |
| Session/Conversation | `conversation` | 用户在该应用下的一次会话 |
| Message | `Conversation.message` JSON | 会话中的 user/assistant 消息 |

公开 API/Agent 还会使用 `API4Conversation`，它与页面 Chat 的 `Conversation` 不是完全相同的表。

`message` 和 `reference` 都是 JSON 字段，当前页面 Chat 没有独立的 Message 数据表。`API4Conversation` 另外保存 `tokens/duration/round/source/dsl` 等公开调用或 Agent 运行信息；不能按页面 Session ID 去这个表里直接寻找同一条记录。

## 2. 前端入口

```text
web/src/pages/next-chats/
  ├─ index.tsx                 聊天应用列表
  ├─ hooks/use-create-chat.ts  创建
  ├─ chat/                     对话页面
  ├─ chat/app-settings/        模型、知识库、Prompt 等配置
  ├─ chat-stream/              SSE 状态
  └─ share/                    分享页
```

请求封装在 `web/src/services/next-chat-service.ts`。发送消息的主要 Hook 是 `use-send-chat-message.ts`。

流式请求由 `web/src/services/chat-completion-stream.ts` 发送并解析，再由 `chat-stream/run-stream.ts` 更新按 Conversation ID 管理的 Store。驱动位于模块级，因此离开聊天页面再返回时，进行中的流仍可更新相同会话状态。

## 3. Chat CRUD

```text
POST   /chats
GET    /chats
GET    /chats/<chat_id>
PUT    /chats/<chat_id>
PATCH  /chats/<chat_id>
DELETE /chats/<chat_id>
DELETE /chats
```

本册路由省略统一的 `/api/v1` 前缀。

创建流程：

```text
创建对话框
  → POST /chats
  → 禁止客户端指定 tenant_id
  → 校验名称和 dataset_ids
  → 解析 Chat/Rerank 模型 ID
  → 合并 prompt 默认值
  → 写 Dialog
  → 返回标准化 Chat DTO
```

`PUT` 更接近完整配置更新，`PATCH` 会对 `llm_setting`、`prompt_config` 做局部合并。删除 Chat 是把 `status` 设为无效，属于软删除。

## 4. `Dialog` 关键配置

| 字段 | 作用 |
|---|---|
| `kb_ids` | 绑定知识库 |
| `llm_id/tenant_llm_id` | Chat 模型 |
| `rerank_id/tenant_rerank_id` | 可选重排模型 |
| `llm_setting` | temperature、top_p、max_tokens 等 |
| `prompt_config` | system、prologue、变量、empty_response |
| `similarity_threshold` | 召回阈值 |
| `vector_similarity_weight` | 文本/向量融合权重 |
| `top_n` | 最终上下文数量 |
| `rerank_candidates_count` | 重排候选窗口 |
| `top_k` | KNN 候选参数 |
| `prompt_config.quote` | 标准 RAG 当前实际读取的引用开关 |
| `do_refer` | 存储模型中存在该字段；不能以它单独判断当前引用行为 |
| `meta_data_filter` | 元数据过滤 |

应用设置页保存的是这些字段，真正发送消息时再读取，构造 `Dialog` 运行上下文。

`prompt_config.parameters` 还声明 Prompt 变量；标准 RAG 只有声明了 `knowledge` 才执行知识检索。`reasoning` 决定 `rag_agent` 进入标准 `async_chat` 还是可多轮调用工具的推理路径；`reference_metadata` 决定是否读取文档元数据并附加到证据和引用中。

## 5. Session CRUD

```text
POST   /chats/<chat_id>/sessions
GET    /chats/<chat_id>/sessions
GET    /chats/<chat_id>/sessions/<session_id>
PATCH  /chats/<chat_id>/sessions/<session_id>
DELETE /chats/<chat_id>/sessions
```

创建 Session 时：

1. 验证 Chat 归属；
2. 生成 `Conversation.id`；
3. 把 Chat 的 `prompt_config.prologue` 写成第一条 assistant 消息；
4. 初始化 `reference=[]`；
5. 保存 `user_id`。

Session 更新接口只允许安全字段，例如名称；不允许通过普通 PATCH 任意覆盖 messages/reference。

## 6. 消息和引用的配对

`Conversation.message` 保存消息数组，`Conversation.reference` 保存每轮回答的检索引用。删除一轮消息时，代码同时删除对应 user/assistant 消息和 reference 项。

这意味着：

- message/reference 顺序必须一致；
- 手工修改 JSON 很容易破坏引用对应关系；
- 引用 Chunk 已从 ES 删除时，历史引用仍可能需要降级展示。

同一轮 user/assistant 共用消息 ID。删除代码找到该 ID 后移除连续的两条消息，以 `(消息索引-1)//2` 删除引用项；开场白本身没有对应 reference。该约定依赖消息顺序，不能把 reference 当成对每一条 message 一一映射的数组。

## 7. Completion 入口

```text
POST /chat/completions
```

主要请求字段：

| 字段 | 说明 |
|---|---|
| `chat_id` | 使用哪一个 Dialog 配置 |
| `session_id`/`conversation_id` | 继续已有会话；没有则创建 |
| `messages` 或 `question` | 输入消息 |
| `stream` | 是否 SSE |
| `pass_all_history_messages` | 是否以请求历史覆盖运行历史 |
| `store_history_messages` | 是否持久化历史 |
| `llm_id` | 可选临时覆盖模型 |

当不保存历史时，必须由调用者传递完整历史，否则模型没有上下文。

当前默认值和约束如下：

| `pass_all_history_messages` | `store_history_messages` | 实际行为 |
|---|---|---|
| false | true | 读取数据库历史，只追加请求最后一条 user 消息，生成结束后保存 |
| true | true | 以请求 `messages` 覆盖运行/保存历史，再加入本轮回答 |
| true | false | 使用调用者历史，不回写会话；需要新会话时也不保存该临时会话 |
| false | false | 参数校验失败 |

`chat_id` 可以为空，此时构造默认临时 Dialog；提供 Session 时必须同时提供 Chat ID，且 Session 的 `dialog_id` 必须匹配。临时覆盖的模型/生成参数作用于本次运行，并不经 Completion 接口保存为应用配置。

## 8. 一次发送消息

```text
前端 use-send-chat-message
  → POST /chat/completions
  → 验证 Chat/Session
  → 追加 user message
  → rag_agent(Dialog, history)
       ├─ reasoning=0 → async_chat
       │    → 改写/检索/TOC与父块/GraphRAG与Web/Prompt/LLM/引用
       └─ reasoning≠0 → RAGTools
            → 模型调用 rag 工具及其推理流程 → 答案/引用
  → SSE 增量事件
  → structure_answer 累积 assistant message/reference
  → 完整生成结束后 ConversationService.update_by_id
  → 前端更新流式状态
```

检索和 Prompt 细节参见[第三册](./03_检索问答与引用.md)。

## 9. SSE 事件

流式接口使用 `text/event-stream`。客户端需要处理：

- 普通 answer delta；
- thinking 开始/结束事件；
- 引用和最终 answer；
- 错误事件；
- 流结束标记。

前端 `chat-stream/run-stream.ts` 和相关 Store 将网络事件转换为页面状态。SSE 连接断开不一定意味着服务端没有保存历史，应重新获取 Session 核对。

普通数据包形如 `data:{"code":0,"message":"","data":{...}}`。`answer` 是增量，思考边界以 `start_to_think/end_to_think` 标志发送；正常最终包为 `final=true` 且 `answer=""`，用于补齐 reference/Prompt。外层再发 `data:true` 结束包。前端合并字段并保留累积正文，不能把结束包误当成新回答。

持久化不是每个 token 一次：`structure_answer()` 先原地更新内存中的 `conv.message/conv.reference`，REST 层在生成器正常结束后整体回写。错误分支发送错误包并跳过该次最终回写；客户端显示了部分内容和数据库保存了完整回答，是两项不同证据。非流式响应则取得完整回答后结构化并回写。

## 10. 反馈、删除和附件

Chat API 还包括：

- 删除单轮消息；
- 点赞/点踩和 feedback；
- TTS；
- ASR；
- 思维导图；
- 推荐问题；
- 会话附件上传。

删除 Session 时会尝试清理该会话上传到对象存储的附件。

## 11. 分享与公开调用

页面分享、Widget、OpenAI 兼容 API 和内部 Chat 页面可能使用不同路由/认证，但最终会加载相同 Chat 配置或对应的公开会话对象。

检查分享问题时要区分：

- 登录用户是否有 Chat 权限；
- 分享 Token/API Token 是否有效；
- `dialog_id` 是否绑定正确；
- 是否写 `Conversation` 还是 `API4Conversation`。

## 12. 权限

读取 Chat 时会遍历当前用户所属租户；修改和删除通常要求所有权。绑定 `kb_ids` 时还要逐个验证知识库可访问性，不能利用一个可访问 Chat 越权查询不可访问知识库。

当前登录用户的 Completion、Session CRUD 也调用 `_ensure_owned_chat()`，并非只要能读取团队中的 Chat 详情就能在该路由下执行回答。知识库权限检查可在创建/更新应用时观察，实际检索范围还由知识库所属 tenant、`kb_ids`、请求文档和元数据过滤共同决定。

## 13. 调试断点

```text
chat_api.session_completion
  → rag_agent
  → async_chat 或 RAGTools
  → Dealer.retrieval
  → kb_prompt
  → LLMBundle.async_chat
  → decorate_answer / structure_answer
  → ConversationService.update_by_id
```

关联字段：`chat_id → session_id → message_id → kb_id → chunk_id`。

## 14. 常见故障

| 现象 | 优先检查 |
|---|---|
| Chat 创建失败 | 默认模型、名称、dataset_ids |
| Session 不属于 Chat | dialog_id 与 chat_id |
| 有历史但模型不记得 | pass/store history 组合、token 截断 |
| 回答无引用 | prompt_config.quote、请求 quote、knowledge 参数、检索结果、最终引用包 |
| SSE 中途断开 | API traceback、代理缓冲、模型连接 |
| 删除后列表仍出现 | status 过滤和缓存失效 |

## 15. 本册检查点

- 能区分 Dialog、Conversation 和 API4Conversation。
- 能解释 Chat 配置如何影响检索与模型。
- 能跟踪一轮消息从前端、SSE 到历史持久化。
- 能说明 messages 与 reference 的对应关系。
- 能区分读取权限和修改所有权。
