# 第十九册：知识库文档核心流程图

本文按当前 Python 主链路画出文件导入、任务创建、解析与索引、文件列表和检索的核心方法。删除链路的逐方法图见[第十八册](./18_知识库文档删除核心方法流程图.md)。图中的 Doc Store 是统一接口；实际落地到 Elasticsearch、Infinity 等，取决于当前 DOC_ENGINE 配置。纯文本流程图可在源码和文档站直接阅读。

先建立整体认识可阅读[第二十一册：知识库 RAG 架构与时序图](./21_知识库RAG架构与时序图.md)，其中包含 PNG 逻辑架构及各链路的 Mermaid 流程图、时序图。本册保留逐方法的细节索引。

## 1. 端到端方法地图

~~~text
上传请求
  → document_api.upload_document
  → FileService.upload_document / web、empty 分支
  → 原文件对象存储 + MySQL Document、File、File2Document
  → 可选的独立 ingest 请求
  → document_api.ingest → _run_sync → DocumentService.run
  → queue_tasks / queue_dataflow → MySQL Task + Redis Stream
  → task_executor.collect → handle_task
  → TaskManager.run_refactored_task → TaskHandler.handle_task
  → ChunkService.build_chunks → EmbeddingService.embed_chunks
  → ChunkService.insert_chunks → Doc Store Chunk
  → 更新 MySQL Task / Document / Knowledgebase 进度与统计

知识库文件列表：document_api.list_docs → MySQL Document + 独立元数据索引
顶部文件管理列表：file_api.list_files → MySQL File + File2Document
检索测试：dataset_api.search_datasets → Dealer.retrieval → Doc Store Chunk
删除：document_api.delete_documents → FileService.delete_docs → DocumentService.remove_document
~~~

上传、解析、列表、检索是四个不同请求；上传成功不代表解析完成，列表查询也不等于检索 Chunk。

## 2. document_api.upload_document：导入入口与类型分流

~~~text
POST /datasets/<dataset_id>/documents
  → 从 Quart request.args 读取 type，缺省 local
  → 查 Knowledgebase，校验团队权限
     ├─ type=local → _upload_local_documents
     │    → 校验 multipart 文件名、可选 parser_config
     │    → 在线程池调用 FileService.upload_document
     │    → 返回 Document 元数据与部分成功错误
     ├─ type=web → _upload_web_document
     │    → 校验名称和 URL → html2pdf → 保存 PDF 对象
     │    → 新建 Document、File、File2Document
     ├─ type=empty → _upload_empty_document
     │    → 校验名称 → 新建 VIRTUAL Document 与 File 关联
     │    → 不写原文件对象
     └─ 其他 type → 参数错误
~~~

入口在 api/apps/restful_apis/document_api.py。web 生成的 PDF 可以有缩略图字段，但它不经过 local 分支的独立 PNG 缩略图上传；empty 是空文档，不是创建空目录。三个分支均不在此处切 Chunk 或生成 Embedding。

## 3. FileService.upload_document：本地文件持久化

~~~text
获取用户根目录 → 知识库目录 → 合并允许覆盖的 parser_config
  → 对每个上传文件：
     ├─ doc_id 已属于其他存活知识库 → 拒绝覆盖
     ├─ 同 doc_id 已存在 → 覆盖原对象、更新大小和 content_hash
     │    → 内容未变则不加入待处理返回列表
     └─ 新文档
          → 检查限额、文件类型和同名冲突
          → 生成 doc_id、对象 key location
          → PDF 必要时预处理
          → STORAGE_IMPL.put(kb.id, location, 原文件二进制)
          → 若生成缩略图，另存 thumbnail_<doc_id>.png
          → DocumentService.insert：写 MySQL document 并增加 KB 文档数
          → add_file_from_kb：写 File 与 File2Document
  → 返回成功的 (Document, binary) 和逐文件错误
~~~

这里的 Document ID 是业务主键；对象存储用 bucket=kb.id、key=location 定位原文件，不能按显示文件名猜关联。代码在 api/db/services/file_service.py。

## 4. FileService.add_file_from_kb：文件树关联

~~~text
输入 Document、知识库目录 ID、tenant_id
  → 按 Document ID 查询 File2Document
     ├─ 已有关联 → 直接返回，避免重复创建 File 节点
     └─ 无关联 → 在 MySQL file 表保存 KNOWLEDGEBASE 来源的文件节点
                → 在 file2document 表保存 file_id ↔ document_id
~~~

File 是文件管理目录树节点，Document 是知识库解析与检索对象；这个方法只建立关系，不写向量。

## 5. document_api.ingest / _run_sync：解析请求

~~~text
POST /documents/ingest
  → ingest 在线程池执行 _run_sync
  → 对全部 doc_id 检查访问权限
  → 对每个 doc_id：
     → 读取 Document 与租户
     → 组装 run、progress 等状态并更新 MySQL document
     ├─ run=CANCEL → 校验任务状态、尝试取消并附加停止信息
     ├─ run=RUNNING 且 delete=true 且旧文档已完成 → 先扣减旧文档/KB 计数
     → 更新 MySQL Document
     → delete=true？是 → 删旧 Task、导航数据和旧 Chunk
     → run=RUNNING？是
          → apply_kb=true 时同步 llm_id/enable_metadata/metadata 等选定配置
          → DocumentService.run → 创建并投递新 Task
       否 → 不生产新 Task
  → 返回“请求已投递”，不等待解析完成
~~~

代码在 api/apps/restful_apis/document_api.py。`delete` 清理不是嵌套在 RUNNING 分支中；请求组合 CANCEL+delete 也可能清理旧数据。取消写标记不代表线程或远端服务已立即停止。上传后是否立即解析取决于前端是否另发 ingest；Debug 上传断点与解析断点需要分开打。

## 6. DocumentService.run / queue_tasks：任务生产

~~~text
DocumentService.run(tenant_id, doc, kb_table_num_map)
  ├─ 有 pipeline_id → queue_dataflow
  └─ 普通文档 → get_storage_address(doc_id) → queue_tasks
                  → 根据文件和 parser 决定任务范围
                     ├─ PDF：按页区间拆分；特定解析模式可不拆
                     ├─ 表格：按行范围拆分
                     └─ 其他：按对应解析策略建任务
                  → 计算配置/内容相关 digest，判断是否可复用
                  → MySQL task 表保存每个 Task，Document begin2parse
                  → 对未完成普通 Task 初始化文档级 pending counter
                  → Redis Stream 仅投递未完成任务，复用成功的 Task 不再投递
~~~

一个 Document 可能对应多个 Task。Task 表在任务生产时就已创建；后续 `update_progress/update_chunk_ids` 是更新同一行，不能把它们当成 Task 首次写入。MySQL 写入与 Redis counter/投递没有统一事务，投递失败可能留下已入库但未执行的 Task。queue_tasks 位于 api/db/services/task_service.py。

## 7. task_executor.collect / handle_task：Worker 消费

~~~text
task_executor.main 循环创建受并发限制的 task_manager
  → task_manager → handle_task → collect
  → 先尝试恢复该消费者未 XACK 的 Pending 消息
  → Pending 耗尽时按队列优先级领取新 Redis 消息
     ├─ 无消息 → 短暂退避，继续下一轮
     └─ 有消息 → 读取消息，用 task.id 从 MySQL 补全执行上下文
                  → 已取消或 Task 不存在？确认消息并跳过
                  → TE_RUN_MODE=0：TaskManager.run_refactored_task
                  → 完成、失败或取消：记录进度与操作日志
                  → 最后 XACK Redis 消息
~~~

StopIteration 表示 Pending 迭代器耗尽，不是任务异常。在 collect 的轮询处打断点会频繁命中；调试单个解析请求可对 task.id/doc_id 加条件断点。代码在 rag/svr/task_executor.py。

## 8. TaskManager.run_refactored_task / TaskHandler.handle：解析分流

~~~text
TaskManager.run_refactored_task
  → 将 Task、限流器、进度与取消回调封装成 TaskContext
  → TaskHandler.handle_task → handle
     ├─ memory → handle_save_to_memory_task 后直接返回
     └─ 其余任务
          → 检查取消标记
          → 绑定 Embedding 模型，探测向量维度
          → _init_kb：创建或校验租户索引及 mapping
          ├─ dataflow / graphrag / raptor / wiki / skill / structure 等 → 各自分支
          └─ 普通文档 → _run_standard_chunking → _run_standard_chunking_impl
~~~

_init_kb 不写 Chunk。Memory 在文档索引初始化前就分流，使用自己的消息索引。`mindmap/evaluation/reembedding/clone` 的对应方法当前有占位完成分支，看到 task_type 或界面入口不等于此执行路径完成了实际计算。TE_RUN_MODE=0 是当前重构执行路径；其他模式见 rag/svr/task_executor.py。实现位于 rag/svr/task_executor_refactor/task_manager.py 和 task_handler.py。

## 9. TaskHandler._run_standard_chunking_impl：普通文档主链

~~~text
按 doc_id 定位 (bucket, object_key) → 从对象存储读完整原文件
  → ChunkService.build_chunks(binary)
  → 无 Chunk？记录进度并执行文档收尾
  → 有 Chunk：
     → EmbeddingService.embed_chunks：给内存 Chunk 附向量
     → ChunkService.insert_chunks：写 Doc Store
     → 表格元数据 / 可选 TOC 等后处理
     → DocumentService.increment_chunk_num：累计文档统计
     → 最后一个分页 Task 执行文档级收尾
     → Task 进度更新，外层 Worker 最后 XACK
~~~

解析得到的 Chunk 在 insert_chunks 前只在 Worker 内存中；不能在 build_chunks 后就去 ES 查。方法位于 rag/svr/task_executor_refactor/task_handler.py。

## 10. ChunkService.build_chunks / run_chunking：解析与切分

~~~text
检查文档大小 → 根据 parser_id 选择解析器
  → 记录 chunk_config（仅用于执行记录/对比）
  → run_chunking
     → 合并表格解析配置
     → 获取 chunk 并发许可
     → 在线程池调用 parser.chunk(原文件、页范围、语言、配置)
     → 返回原始内存 Chunk
  → 提取 PDF outline，写独立文档元数据
  → 补稳定 Chunk ID、doc_id、kb_id、时间，保留解析器生成的分词与位置
  → Chunk 图片二进制单独写对象存储，Chunk 留 img_id
  → 按配置生成关键词/问题，修改内存 Chunk
  → 自动元数据启用且配置字段时：汇总 metadata_obj → 独立文档元数据索引
  → 标签知识库配置存在时：补 Chunk 标签
  → 返回待 Embedding 的 Chunk 列表
~~~

解析器的 chunk() 内部负责文件内容提取及切分；build_chunks 负责统一协调和后处理。`content_ltks/content_sm_ltks`、标题分词、页码/位置通常来自解析器；关键词和问题随普通 Chunk 写入，`metadata_obj` 汇总后删除，最终 `meta_fields` 由 DocMetadataService 写独立索引。PDF outline 写元数据另有路径，不依赖自动元数据开关。代码在 rag/svr/task_executor_refactor/chunk_service.py、chunk_builder.py 与 chunk_post_processor.py。

## 11. EmbeddingService.embed_chunks / ChunkService.insert_chunks：向量落地

~~~text
embed_chunks(chunks, embedding_model, parser_config)
  → 优先以 question_kwd 作为内容，缺省使用 content_with_weight
  → 批量编码内容，按 filename_embd_weight 与标题向量加权组合
  → 把向量写入内存 Chunk 的 q_<维度>_vec 字段
  → 返回 token_count 与向量维度

insert_chunks(task_id, tenant_id, kb_id, chunks)
  → 按文档启用状态设置 Chunk 可检索性
  → 有母块时先创建并写入母块
  → 分批写入普通 Chunk
  → 每批调用 settings.docStoreConn.insert
  → 周期 checkpoint 和尾批更新 MySQL Task.chunk_ids，保存已写入的主 Chunk ID
  → 支持 refresh_idx 的后端最后统一 refresh
  → 返回全部批次是否成功
~~~

Chunk 文本、倒排检索字段和向量字段一起写 Doc Store；原文件与 Chunk 图片仍在对象存储。`docStoreConn.insert()` 返回空列表表示该批成功，非空列表是错误详情。批量写入用 `refresh=False`，最终刷新与“请求已写入”的时间点应区分；实际后端按 DOC_ENGINE 选择。

Task 行已在 queue_tasks 时创建，`chunk_ids` 不是新建任务，也不逐批更新。当前 `TaskService.update_chunk_ids()` 使用普通 UPDATE，没有检查受影响行数；Task 已被并发删除时不会自动抛 `DoesNotExist`。因此虽然 `_update_task_chunk_ids()` 有异常失败回滚分支，不能宣称它对“Task 已删除”的情况提供可靠回滚保证。母块、TOC 与普通块也不是由这一字段统一完整记账。

## 12. document_api.list_docs / _get_docs_with_request：知识库文件列表

~~~text
GET /datasets/<dataset_id>/documents
  → list_docs 校验知识库访问权限
     ├─ type=filter → _get_doc_filters_with_request
     │    → 统计类型、状态等筛选项，不返回分页文档
     └─ 普通列表 → _get_docs_with_request
                    → 校验分页、排序、名称、类型、run 状态
                    → 若有 metadata 条件，先从独立元数据索引取 doc_id
                    → DocumentService.get_by_kb_id
                    → 整理缩略图 URL、source_type、元数据配置
                    → 返回 docs 与 total
~~~

这是知识库详情页的文件列表，不是全文/向量召回。分块数、Token 数、run/progress 来自 MySQL Document。代码在 api/apps/restful_apis/document_api.py。

## 13. DocumentService.get_by_kb_id：列表主体与元数据补充

~~~text
MySQL document
  → 联接 file2document、file、UserCanvas、User
  → 按 kb_id、doc_id、关键词、类型、run、后缀等过滤
  → count 得 total
  → 排序、分页，得到当前页 Document
  → DocMetadataService.get_metadata_for_documents(当前页 doc_id)
     → 从 ragflow_doc_meta_<tenant_id> 独立元数据索引取 meta_fields
  → 按 doc_id 合并元数据，返回 docs / total
~~~

列表不读取普通 Chunk 索引。只有元数据筛选或展示涉及独立的元数据索引；即使 ES 中有 Chunk，也不会被当成列表行。代码在 api/db/services/document_service.py。

## 14. file_api.list_files：顶部「文件管理」列表

~~~text
GET /files
  → file_api.list_files → file_api_service.list_files
  → 无 parent_id？获取租户根目录并初始化知识库/Skills 虚拟目录
  → 校验目标目录
  → FileService.get_by_pf_id：查 MySQL file 子节点或按关键词搜索
  → 补文件关联知识库信息与父目录
  → 返回 files / total / parent_folder
~~~

此处列表主对象是 File，知识库详情页列表主对象是 Document；二者通过 File2Document 关联，均不执行 Chunk 召回。代码在 api/apps/restful_apis/file_api.py 与 api/apps/services/file_api_service.py。

## 15. search_datasets / Dealer.retrieval：检索测试

~~~text
POST /datasets/search 或 /datasets/<id>/search
  → 校验知识库权限与 Embedding 模型兼容性
  → 可选元数据过滤、跨语言改写、关键词与标签增强
  → Dealer.retrieval
     → Dealer.search 构造全文表达式与查询向量
     → Doc Store 根据 kb_id/doc_id/available_int 等过滤并召回 Chunk
     → 过滤指向已删除 Document 的残留 Chunk
     → 按后端能力融合词法与向量信号，可选 Rerank 模型
     → 应用相似度门槛、分页与文档聚合
  → 可选知识图谱/子 Chunk 增强 → 返回 Chunk 和标签
~~~

检索入口返回相关 Chunk，不调用 Chat 模型生成最终答案。Dealer.search 位于 rag/nlp/search.py；不同 Doc Store 后端的全文、KNN 和融合实现不能简单视作完全相同。

## 16. 调试断点路线

| 目标 | 先打断点 | 后续断点 |
|---|---|---|
| 上传 | upload_document | _upload_local_documents → FileService.upload_document → add_file_from_kb |
| 解析请求 | ingest | _run_sync → DocumentService.run → queue_tasks |
| Worker | collect 中确认 task.id | handle_task → TaskManager.run_refactored_task → TaskHandler.handle |
| Chunk/Embedding | _run_standard_chunking_impl | build_chunks → run_chunking → embed_chunks → insert_chunks |
| 知识库文件列表 | list_docs | _get_docs_with_request → get_by_kb_id → get_metadata_for_documents |
| 文件管理列表 | file_api.list_files | file_api_service.list_files → FileService.get_by_pf_id |
| 检索测试 | dataset_api.search_datasets | dataset_api_service.search_datasets → Dealer.retrieval → Dealer.search |
| 删除 | delete_documents | 见[第十八册](./18_知识库文档删除核心方法流程图.md) |

以上方法名均以当前 Python 代码为准。Worker 是独立进程，API 断点不会自动捕获其任务消费。
