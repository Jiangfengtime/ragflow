## 4. 核心关联关系

```text
User ─< UserTenant >─ Tenant
Tenant ─< Knowledgebase ─< Document ─< Task
```

## 6. `TE_RUN_MODE`

Task Executor 在 `handle_task` 中读取环境变量：

| 值 | 行为 |
|---|---|
| `0` | 默认，执行重构后的 `TaskManager.run_refactored_task` |
| `1` | 对比模式，先运行旧流程，再拦截新版写操作并比较 |
| 其他 | 执行旧版 `do_handle_task` |

正常学习当前主路径使用 `0`。对比模式更慢，主要用于重构迁移验证。

## 10. Chunk 函数索引

### 10.1 `ChunkService.build_chunks`

```python
async def build_chunks(storage_binary: bytes, on_chunking_start=None)
```

| 参数 | 含义 |
|---|---|
| `storage_binary` | 从对象存储读取的完整原文件 bytes |
| `on_chunking_start` | 取得解析并发许可后的可选回调 |

核心行为：

```text
文件大小检查
  → 根据 parser_id 选择 parser
  → 记录有效 chunk_config
  → 在线程池执行同步 parser
  → 标准化 Chunk
  → 保存图片等派生对象
  → 关键词/问题/标签/metadata 增强
  → 返回内存中的 Chunk 列表
```

`recording_context.record("chunk_config", ...)` 只记录执行上下文用于对比/诊断，不是持久化 Chunk。

### 10.2 `ChunkService.insert_chunks`

```python
async def insert_chunks(
    task_id,
    task_tenant_id,
    task_dataset_id,
    chunks,
    doc_bulk_size=None,
)
```

| 参数 | 含义 |
|---|---|
| `task_id` | 当前 MySQL Task ID |
| `task_tenant_id` | 用于确定 tenant 索引 |
| `task_dataset_id` | `kb_id`，用于过滤/分区 |
| `chunks` | 已完成增强和 Embedding 的 Chunk |
| `doc_bulk_size` | 可选 Bulk 批大小，默认使用 settings |

该方法创建必要的 mother chunk，分批调用 `docStoreConn.insert`，保存 `Task.chunk_ids` 检查点并处理回滚。

## 13. `validate_dataset_embedding_models(kbs)`

位置：`api/db/services/knowledgebase_service.py`。

功能：

1. 要么所有数据集都配置 Embedding，要么都不配置；不能混合。
2. 解析 `tenant_embd_id` 或历史 composite model name。
3. 比较基础模型名。
4. 多于一种模型时返回错误字符串，否则返回 `None`。

它验证的是模型标识兼容性，不会对每条 Chunk 做实时维度扫描。

## 15. `Dealer.search` 参数

```python
async def search(
    req,
    idx_names,
    kb_ids,
    emb_mdl=None,
    highlight=None,
    rank_feature=None,
    min_match=True,
)
```

| 参数 | 含义 |
|---|---|
| `req` | 内部统一查询参数 |
| `idx_names` | 目标 Doc Store 索引名 |
| `kb_ids` | 数据集过滤 |
| `emb_mdl` | 生成查询向量；无向量模式可为空 |
| `highlight` | 高亮字段开关/列表 |
| `rank_feature` | 标签和 PageRank 相关特征 |
| `min_match` | 是否为文本 query_string 设置最低匹配比例 |

`min_match = vector_similarity_weight < 0.8` 的含义是：当检索并非几乎纯向量时，对全文条件保留最低词项匹配约束；向量权重很高时放宽文本必须命中的要求，避免语义相关但词面不同的候选被提前排除。

## 16. BM25、KNN 与融合速查

```text
第一阶段 ES 查询
  ├─ query_string / MatchTextExpr → 倒排索引、BM25 风格候选
  └─ MatchDenseExpr / KNN         → HNSW 近似向量候选

候选返回应用层
  ├─ token_similarity            → 重新计算词项覆盖分
  ├─ _knn_scores                 → 对候选取纯向量分
  ├─ rank_feature                → 标签/PageRank 加分
  └─ final = text_weight * term
           + vector_weight * vector_or_rerank
           + rank_feature
```

第一阶段 BM25 `_score` 主要用于形成候选；当前默认 ES 路径的最终文本项是 Python `token_similarity`，不能把两者当成同一个分数。

## 17. `rerank_by_model`

输入：query、候选 Chunk 文本、权重和 rank feature。

过程：

1. 对 query 分词；
2. 组合 Chunk 正文、标题和重要关键词；
3. 计算本地 `token_similarity`；
4. 调用 `rerank_mdl.similarity(query, docs)`；
5. 加入标签/PageRank；
6. 返回最终分、词项分和 Rerank 分。

公式：

```text
final = (1 - vector_similarity_weight) * token_similarity
      + vector_similarity_weight * rerank_score
      + rank_feature
```

配置 Rerank 后，Rerank 分替代最终融合中的普通向量余弦项，但第一阶段仍需要召回足够多的候选。

## 18. 跨语言与标签

### `cross_languages`

当选择 Chinese、English 等语言时，它将原问题翻译/扩展为多个语言文本，再拼成一个最终查询字符串。不是为每种语言分别执行一遍完整 `retrieval`。

### `label_question`

从配置的标签知识库或标签信息中为问题生成匹配标签。结果作为 `rank_feature` 影响第一阶段或最终加分，通常不是硬过滤条件。

## 21. 阅读返回值时的注意点

- Peewee `query(...)` 通常返回列表，即使条件看起来唯一；需要单条时用明确的 get/filter 接口。
- `get_by_id` 常返回 `(exists, object)`，不要把 tuple 当对象。
- Service 搜索函数可能返回 `(success, data_or_error)`。
- ES Python Client 返回 `ObjectApiResponse`，核心 JSON 在 `.body`。
- Redis 无消息返回 `None` 是正常空轮询。
- `run_in_executor` 返回 awaitable，真正实现在线程中的目标函数。
