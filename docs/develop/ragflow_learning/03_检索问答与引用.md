# 第三册：检索、问答与引用

摄取解决“把文档变成可检索数据”，本册解决“怎样从这些数据中找到证据并生成可追溯答案”。知识库检索测试的逐方法流程图见[第十九册](./19_知识库文档核心流程图.md)。

## 1. 一次 RAG 请求的阶段

```text
原始问题
  -> 会话与助手配置
  -> 问题改写/跨语言/关键词增强
  -> 权限与数据集过滤
  -> 词法召回 + 向量召回
  -> 融合与重排
  -> 阈值和数量裁剪
  -> 可选 TOC/父子块/KG/Web 增强
  -> 知识上下文格式化
  -> Prompt 预算控制
  -> LLM 流式生成
  -> 引用识别或回填
  -> 保存会话与统计
```

回答质量是整条链路的乘积。不能只通过更换 Chat Model 解决召回错误。

## 2. Doc Store 抽象

`common/doc_store/doc_store_base.py::DocStoreConnection` 统一定义：

- 健康检查；
- 索引创建与删除；
- `search`；
- `get`、`insert`、`update`、`delete`；
- total、fields、highlight、aggregation 等结果读取；
- 部分后端的 SQL 能力。

业务层以表达式描述意图：

| 表达式 | 意义 |
|---|---|
| `MatchTextExpr` | 全文/关键词匹配 |
| `MatchDenseExpr` | 稠密向量相似度 |
| `MatchSparseExpr` | 稀疏向量匹配 |
| `MatchTensorExpr` | 多向量或张量匹配 |
| `FusionExpr` | 多路分数融合 |
| `OrderByExpr` | 明确排序 |

不同后端可以用自身 DSL 实现同一意图，但分数尺度和能力边界并不保证完全一致。

## 3. `Dealer.search()`

`rag/nlp/search.py::Dealer` 是 Python 检索主入口。

### 3.1 过滤条件

`get_filters()` 从请求中提取 `kb_ids`、`doc_ids`、`available_int` 等条件。过滤先于相似度排序，它是“0 或 1”的候选资格判断。

最常见的零召回原因之一不是向量质量，而是：

- 错误的 tenant index；
- kb_id 不匹配；
- doc_ids 范围为空；
- chunk 被标记为不可用；
- 文档已删除但残留索引或反向情况。

### 3.2 词法查询

`FulltextQueryer.question()` 对问题分词并构造全文表达式。词法检索擅长：

- 产品型号；
- 人名、缩写、错误码；
- 精确术语；
- 文档中原样出现的关键词。

查询器同时做繁简/全半角标准化、词权重和同义词扩展，并查询多个增强字段。当前字段权重是 `title_tks^10`、`title_sm_tks^5`、`important_kwd^30`、`important_tks^20`、`question_tks^20`、`content_ltks^2`、`content_sm_ltks`。因此摄取阶段生成的关键词和问题会参与召回；它们并非只用于页面展示。此处的分词/同义词扩展与后文可选的 LLM 关键词增强是两个步骤。

### 3.3 向量查询

`get_vector()` 调用 `emb_mdl.encode_queries`，根据维度选择 `q_<dim>_vec`，以 cosine 构造 `MatchDenseExpr`。

向量检索擅长语义近似，但必须满足：

1. 查询和 chunk 使用兼容的 Embedding 模型；
2. 维度一致；
3. 文本预处理合理；
4. 候选池足够大。

### 3.4 候选池与分页

`knn_top_k` 与 `knn_num_candidates` 控制近邻搜索候选；页面 `size` 控制返回记录数。候选池太小可能让后续重排没有机会看到正确证据。

## 4. 混合检索

混合检索不是把 BM25 分数和 cosine 分数直接相加这么简单。不同后端可能使用加权和、归一化 Pipeline 或结果级融合。

当前 ES 路径分两阶段：

```text
Dealer.search
  → MatchTextExpr + MatchDenseExpr + FusionExpr
  → ES query_string + knn，先取候选窗口
Dealer.retrieval
  → 删除残留候选校验
  → 对这些候选 ID 再执行 KNN-only 查询
  → Python 词项匹配 + 引擎 KNN 分数 + 标签/PageRank
  → 最终阈值、稳定排序和分页
```

第一阶段 ES 使用固定 `weights="0.001,1"`，当前适配器读取第二个权重来设置 `bool.boost=1-vector_weight`，这里实际为 `0`；不能把它解释成用户配置的最终 BM25/向量加权公式。`query_string` 仍进入 `knn.filter`，会约束向量候选。第二阶段才应用用户的 `vector_similarity_weight`：

```text
hybrid_score = (1 - vector_similarity_weight) × token_similarity
             + vector_similarity_weight     × knn_score
             + rank_features
```

这里的 `token_similarity` 由 Python 重算，正文词项去重后，还会加入标题×2、重要关键词×5、生成问题×6；它不是 Lucene 原始 BM25 `_score`。`knn_score` 则是 `get_scores()` 读取的引擎原始 `_score`，代码没有在此将它反变换为数学上的原始 cosine。第二次 KNN 只过滤第一阶段候选 ID，不会扩大召回范围。

Infinity 未配置专用 Rerank 时直接使用引擎融合分数；OceanBase/SereneDB 使用返回的 Chunk 向量本地重排；GaussDB 使用 SQL 融合分数并叠加本地标签分数。后端间的分数尺度需要分别观察。

`vector_similarity_weight` 高：更偏语义相似；低：更偏关键词。它不是“答案正确率”旋钮，应该基于查询类型调优。

## 5. `Dealer.retrieval()`

`retrieval()` 在底层 search 之上承担完整召回策略：

1. 组装请求和字段；
2. 执行候选搜索；
3. 过滤指向已删除 Document 的残留 chunk；
4. 选择 KNN/内置混合重排或专用 Rerank 模型；
5. 应用相似度门槛；
6. 截取 top_n；
7. 生成文档聚合和用于 API 的 chunk 结构。

`retrieval()` 没有单独的 `top_n` 入参，Chat 将 `Dialog.top_n` 传成 `page_size`。每次先读取第一个 `rerank_candidates_count` 候选窗口，再在重排结果上分页；要求 `page × page_size <= rerank_candidates_count`，配置专用 Rerank 时只允许 `page=1`。

返回的 `total` 和 `doc_aggs.count` 只统计候选窗口内通过最终阈值的 Chunk，不是整个索引的潜在命中总数。TOC、父块合并或 KG 补充发生在它们之后，也不会自动重新计算这些计数。

### 参数边界

| 参数 | 所在阶段 | 调高的主要代价 |
|---|---|---|
| `knn_top_k` | 向量召回 | 搜索成本和候选量 |
| `rerank_candidates_count` | 重排输入 | Rerank 时间/费用 |
| `top_n` | 最终上下文 | LLM 输入 token |
| `similarity_threshold` | 最终过滤 | 调高会降低召回率 |
| `vector_similarity_weight` | 融合/重排 | 可能弱化精确关键词 |

`similarity_threshold` 同时作为第一阶段 KNN 门槛和第二阶段融合分数门槛；`vector_similarity_weight <= 0` 时最终门槛改为 `0`。向量权重设为 `0` 仍会绑定 Embedding、发起候选向量查询，不能据此判断调用链已经成为只查倒排索引。

## 6. Rerank

代码提供多种路径：

- `rerank_with_knn`：利用检索引擎返回的 KNN 分数；
- `rerank`：本地结合 token 和向量相似度；
- `rerank_by_model`：使用专用 Rerank 模型。

配置专用模型后，最终公式仍为“词项分数×文本权重 + Rerank 模型分数×向量权重 + 标签/PageRank”。返回字段 `vector_similarity` 此时装的是模型相关性分数，不再是 Embedding 相似度；只打开 Rerank 并不意味着最终排序完全由该模型决定。

Cross-encoder 类型的 Rerank 往往更精确，但需要对问题和每个候选共同推理。正确使用方式通常是“大候选召回 + 小规模精排”，不是对整个知识库逐块计算。

## 7. 聊天入口与配置加载

REST 入口：

```text
api/apps/restful_apis/chat_api.py::session_completion
```

核心生成服务：

```text
api/db/services/dialog_service.py::rag_agent
  ├─ reasoning=0 → async_chat
  └─ reasoning≠0 → RAGTools 与推理工具调用
```

它会加载：

- Dialog 的知识库与 Prompt 配置；
- Chat、Embedding、Rerank、TTS 等模型；
- Conversation 历史；
- 请求指定的文档范围与引用元数据；
- Web Search、KG、TOC 等开关。

标准 `async_chat` 无知识库且未启用 Web Search 时走 `async_chat_solo`。知识检索还要求 `prompt_config.parameters` 含 `knowledge`；模板正文写了 `{knowledge}` 与参数列表声明了 `knowledge` 是两个需要分别检查的条件。

## 8. 问题预处理

进入检索前可能执行：

### 多轮问题改写

“它的保修期呢？”离开历史上下文无法检索。`refine_multiturn` 会把省略指代的问题转换为独立问题。

### 跨语言扩展

查询语言与知识库语言不同，可生成目标语言版本以改善召回。

`cross_languages()` 将原问题和目标语言文本拼成一次检索字符串，不是为每种语言各执行一次召回。

### 关键词增强

LLM 提取关键词后附加到查询，帮助词法召回。代价是额外模型调用和延迟。

调试时必须记录“原始用户问题”和“最终送入 retriever 的问题”，否则可能在错误对象上分析。

## 9. 检索增强分支

基本 chunks 之外还可能加入：

- `retrieval_by_toc`：利用目录结构寻找相关章节；
- `retrieval_by_children`：按命中子块的 `mom_id` 取回父块，将同一父块的多个子块合并为较完整上下文；父块缺失时保留子块；
- Web Search：加入互联网结果；
- KG Retrieval：加入实体关系知识；
- SQL Retrieval：针对有字段映射的数据集生成查询。

任何增强都要保留来源和范围，避免不同租户或不同数据集的信息错误混合。

TOC 会先根据已有命中挑选一个文档，再让 LLM 根据其目录选相关 Chunk；父块合并使用子块平均分而不重新计算问题与父块的相关性。SQL 分支则在存在知识库 `field_map` 时先尝试 `use_sql()`，成功可提前返回，发生在普通向量召回之前。不同入口的增强开关并不完全相同，Search App 的两条请求链见[第十四册](./14_搜索应用完整链路.md)。

## 10. `kb_prompt()` 与上下文

`kb_prompt()` 把结构化 chunk 转换成模型可读文本。通常保留：

- 文档名称；
- chunk 内容；
- 引用编号；
- URL（存在时）；
- `document_metadata`（已请求富集时）。

当前 `kb_prompt()` 不直接输出 `positions/page_num_int`，位置主要随 reference 返回给前端做原文定位。`reference_metadata` 是读取并附加文档元数据的查询配置，与摄取时启用元数据生成的配置要分开理解。

上下文不是越多越好。大量低相关 chunk 会：

- 稀释正确证据；
- 增加 token 和延迟；
- 诱导模型拼接冲突内容；
- 增大引用匹配难度。

## 11. Prompt 组装和预算

生成消息包含：

```text
system prompt
  + knowledge
  + citation instruction
  + conversation history
  + current user message
  + text/image attachments
```

`message_fit_in()` 按模型上下文限制裁剪消息，并为输出保留空间。若配置了知识但 Prompt 未显式使用 `{knowledge}`，当前代码会在适当条件下把知识追加到 system content，避免“检索到了但模型没看到”。

具体裁剪顺序是：超预算先只保留 system 和最后一条消息，仍超预算再裁剪这两条的内容。`async_chat` 以模型上限的 95% 调用它，并用剩余 token 限制生成 `max_tokens`。因此数据库里保存了历史，不代表每轮都完整发送给模型。

## 12. 模型适配

`LLMBundle` 根据租户配置解析模型实例，再调用 `rag/llm` 中对应能力。

模型类型应分开理解：

| 类型 | 输入输出 | 在 RAG 中的职责 |
|---|---|---|
| Chat | messages → text | 问题改写与答案生成 |
| Embedding | text → vector | 摄取和查询编码 |
| Rerank | query + docs → scores | 候选精排 |
| CV | image + text → text | 视觉理解 |
| ASR | audio → text | 音频转录 |
| TTS | text → audio | 答案语音化 |

供应商只是实现，能力类型才是业务依赖。

## 13. 流式响应

流式调用通过异步生成器不断产出增量。需要同时处理：

- 首 token 延迟；
- reasoning 与 answer 的区分；
- 客户端断开；
- 中途异常；
- 最终 reference 和 token 统计；
- 会话持久化时机。

只看到前端文本逐字出现，不能证明最终事件和引用已经正确完成。

当前流式协议的正文事件是 `answer` 增量、`final=false`，思考边界使用 `start_to_think/end_to_think`。标准 Chat 与 Search 摘要生成完成后，最终事件将 `answer` 置为空字符串，主要携带引用、Prompt 等收尾信息；REST 外层随后发送 `data:true` 表示流结束。客户端应累加正文并合并最终引用，不能用空的最终 `answer` 覆盖已显示正文。

## 14. 引用生成

模型可能按提示直接生成引用标记。如果没有生成可识别标记，系统会：

1. 按需取回候选 chunk 的向量；
2. 切分或分析答案；
3. 用词法与向量相似度匹配答案片段和 chunk；
4. 插入引用标记；
5. 按引用文档缩小 `doc_aggs`；未匹配到引用文档时保留原聚合。

当前 reference 的 `chunks` 仍保留候选集合，供编号索引和来源展示使用，并不是仅含实际引用 Chunk 的精简列表；响应前会移除向量。标准 Chat 的生成/回填开关实际是 `prompt_config.quote` 与请求 `quote`，不能只检查 `Dialog.do_refer` 字段。

还要核对流式边界：`decorate_answer()` 会得到可能回填引用标记的完整答案，但正常流式最终事件把这个正文清空，历史通过此前的增量累积。由此不能假设生成后补出的标记一定会重写浏览器正文或会话正文；应同时检查原始增量、最终 reference 和保存的消息。

因此引用质量至少依赖：候选证据正确、chunk 粒度合理、答案忠于证据、引用匹配阈值合理。

## 15. 质量诊断矩阵

| 现象 | 可能阶段 | 验证方法 |
|---|---|---|
| 正确 chunk 完全没出现 | 召回 | 直接调用 retrieval test，放宽阈值 |
| 正确 chunk 排名很低 | 融合/重排 | 比较词法、向量、rerank 分数 |
| 证据正确但答案错误 | Prompt/LLM | 检查实际 system prompt 和上下文 |
| 答案正确但引用错 | 引用回填 | 检查最终候选与 marker |
| 多轮第二问失败 | 问题改写 | 打印最终检索 query |
| 延迟高 | 多阶段 | 分别记录改写、Embedding、Search、Rerank、LLM 时间 |

## 16. 实验：建立最小检索评测集

准备 20 个问题，每题记录：

- 标准答案；
- 必须命中的文档和段落；
- 允许的同义表达；
- 不应该使用的冲突文档。

每次实验保存：Recall@K、正确 chunk 排名、最终引用、回答正确性和总延迟。一次只改变一个参数，避免无法归因。
