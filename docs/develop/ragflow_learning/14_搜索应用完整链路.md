# 第十四册：搜索应用完整链路

“搜索”一级菜单是一个可保存、可分享、可生成摘要的检索应用。它不同于知识库 Testing 页面：Testing 主要观察 Chunk，Search App 还保存产品配置并可流式生成结果。

## 1. 前端结构

```text
web/src/pages/next-search/
  ├─ index.tsx                 Search 应用入口
  ├─ search-home.tsx           初始页
  ├─ searching.tsx             查询运行页
  ├─ search-view.tsx           结果展示
  ├─ search-setting.tsx        配置
  ├─ retrieval-documents/      召回文档/Chunk
  ├─ mindmap-sheet.tsx         思维导图
  ├─ embed-app-modal.tsx       嵌入/分享
  └─ share/                    分享页
```

应用列表实际在 `web/src/pages/next-searches/`；`next-search/` 管理单个应用的配置和查询页。请求封装在 `web/src/services/search-service.ts`，查询调度在 `next-search/hooks.ts`。

## 2. 数据模型

`Search` 表主要字段：

| 字段 | 含义 |
|---|---|
| `id` | Search App ID |
| `tenant_id/created_by` | 所有者 |
| `name/description/avatar` | 展示信息 |
| `search_config` | 数据集、检索、摘要和页面功能配置 |
| `status` | 有效状态 |

`search_config` 是 JSON，包含 `kb_ids/doc_ids`、阈值、向量权重、Rerank、top_k、Chat 模型参数、跨语言、关键词、Web Search、Related Search 和 Mindmap 等。

配置字段存在于模型或表单中，并不表示每条查询路径都会消费它；本册第六节按当前调用代码区分。`Search` 只保存应用配置，没有 `Conversation.message/reference` 式多轮会话字段，当前 Completion 也不保存每次查询的聊天历史。

## 3. CRUD 接口

```text
POST   /searches
GET    /searches
GET    /searches/<search_id>
PUT    /searches/<search_id>
DELETE /searches/<search_id>
```

本册路由省略统一的 `/api/v1` 前缀。

创建只要求名称，完整 `search_config` 可在设置页更新。更新接口会将传入 config 与当前 config 浅合并，嵌套字段是否完整保留取决于前端提交结构。

删除当前调用 `SearchService.delete_by_id`，与 Chat 的软删除实现不同，阅读代码时不要假设所有应用都只改 `status`。

## 4. Completion 接口

```text
POST /searches/<search_id>/completion
POST /searches/<search_id>/completions
```

两个 URL 指向同一实现。请求至少包含 `question`。

```text
search_id
  → SearchService.get_detail
  → 读取 search_config
  → 决定 kb_ids
  → 验证每个知识库权限
  → async_ask(question, kb_ids, tenant, search_config, search_id)
  → SSE 返回答案、引用与最终标记
```

## 5. 与 `search_datasets` 的关系

页面发出两条独立请求，共用底层 Dealer，却在不同入口准备查询和配置：

```text
next-search/hooks.ts::sendQuestion
  ├─ 始终执行 Chunk 结果请求
  │    → POST /datasets/search（search_id + dataset_ids）
  │    → dataset_api_service.search_datasets
  │    → Dealer.retrieval → 可选 KG → 父块合并 → 返回结果列表
  └─ summary=true 才执行 AI 摘要请求
       → POST /searches/<search_id>/completions
       → dialog_service.async_ask
       → Dealer.retrieval → ASK_SUMMARY → Chat LLM → SSE 与引用
```

`async_ask()` 直接调用 Retriever，不经过 `search_datasets()`。摘要通常重新召回最多 12 个 Chunk，采用 `ASK_SUMMARY` 模板，并在引用回填时固定使用词项权重 0.7、向量权重 0.3。它不是对浏览器当前显示的分页结果直接生成摘要。BM25、KNN、融合和 Rerank 仍按[第三册](./03_检索问答与引用.md)执行。

`search_id` 在结果链用于加载保存配置，在摘要链作为追踪 ID。两条链的查询增强、文档过滤和返回数量可能不同，“结果页命中的 Chunk”和“摘要使用的 Chunk”需要分别检查。

## 6. 配置分组

### 检索范围

- `kb_ids`；
- `doc_ids`；
- metadata filter；
- 是否包含知识编译产物。

结果链读取请求的 `doc_ids`，从保存配置读取元数据过滤；摘要链读取保存配置的 `doc_ids` 和元数据过滤。`include_knowledge_compilation=false` 目前是结果链请求参数，传成 `must_not exists compile_kwd`；摘要链没有传递这个排除条件。

### 相关性

- `similarity_threshold`；
- `vector_similarity_weight`；
- `top_k`；
- `rerank_id`；
- `rerank_candidates_count`。

### 查询增强

- `cross_languages`；
- `keyword`；
- `use_kg`；
- `web_search`；
- `related_search`。

当前消费边界如下：

| 能力 | Chunk 结果链 `search_datasets` | AI 摘要链 `async_ask` |
|---|---|---|
| 阈值、向量权重、Rerank、候选数 | 从保存配置加载 | 从保存配置加载 |
| 跨语言/LLM 关键词 | 读取 `cross_languages/keyword` 并扩展问题 | 当前未执行这些扩展 |
| `use_kg` | 普通召回后额外插入图谱上下文 | 当前未按该开关追加图检索 |
| 父子块 | 命中子块后按 `mom_id` 合并为父块 | 当前未调用父块合并 |
| `reference_metadata` | 当前结果服务未做此富集 | 当前支持读取文档元数据并附加到引用/Prompt |
| `highlight` | 页面请求该值；当前结果服务未转交给 `retrieval` | 当前未开启高亮 |
| `web_search` | 当前结果服务未调用 Web Search | 当前摘要服务未调用 Web Search |

跨语言还存在字段映射边界：当前 `Search` 模型默认值和设置表单使用 `chat_settingcross_languages`，结果服务读取 `cross_languages`，需要检查实际保存 JSON 是否含服务所读的键。保存设置时表单对 `doc_ids/use_kg/highlight/keyword/chat_settingcross_languages` 的初值也使用固定空值或 false，应同时比较载入配置、表单和 PUT body。

### 展示/生成

- `summary`；
- Chat 模型和生成参数；
- `highlight`；
- `query_mindmap`。

`summary` 是前端是否发摘要请求的开关；直接调用 Completion 时，服务本身仍进入摘要流程。Related Search 和 Mindmap 是额外请求：内部页面分别调用 `/chat/recommendation`、`/chat/mindmap`，分享页调用 `/searchbots/related_questions`、`/searchbots/mindmap`，不是主 Completion 中自动生成的字段。

## 7. Search 与 Chat 的区别

| 维度 | Search App | Chat App |
|---|---|---|
| 核心模型 | `Search` | `Dialog` |
| 主要交互 | 单次查询/结果页 | 多轮 Conversation |
| 历史 | 不以 Conversation 为核心 | 保存 Session 和消息 |
| 配置重点 | 检索、摘要、Web/相关搜索 | Prompt、LLM、多轮、引用 |
| 共同底座 | Dealer、知识库、Embedding、Rerank | Dealer、知识库、Embedding、Rerank |

## 8. 权限与分享

Search 详情会在当前用户所属租户中查找；修改、删除以及当前登录 Completion 要求 `SearchService.accessible4deletion()` 所校验的所有权。Completion 还逐个验证所用 `kb_ids` 的可访问性。

分享页面位于 `next-search/share/`，走 `/searchbots/*` 和 `AUTH_BETA` 认证路径，由 `add_tenant_id_to_kwargs` 装载身份；它与内部登录 `/searches/*` 是不同入口，应独立检查 Token、保存配置、知识库范围和各入口的校验行为。

## 9. 调试入口

```text
next-search hooks
  ├─ knowledge-service.retrievalTest → dataset_api.search_datasets
  │    → dataset_api_service.search_datasets → Dealer.retrieval → JSON
  └─ search_api.completion → async_ask
       → Dealer.retrieval → Chat LLM → SSE
```

关键 ID：`search_id → kb_ids → doc_ids → chunk_ids`。

日志：

```text
知识库检索已开始 检索ID=...
检索候选集已获取 跟踪ID=...
检索候选集排序完成 跟踪ID=...
知识库检索完成 检索ID=...
搜索应用召回完成 搜索应用ID=...
搜索应用引用已构建 搜索应用ID=...
```

摘要 SSE 和 Chat 类似：正文增量 `final=false`，思考开始/结束标志，最终 `final=true` 包的 `answer=""` 携带 reference，之后 REST 外层发 `data:true`。两个请求都成功，才说明结果列表和 AI 摘要完整跑通。

## 10. 常见故障

| 现象 | 检查 |
|---|---|
| 保存后配置丢失 | PUT body、浅合并、嵌套字段 |
| Search 无数据 | kb_ids、权限、ES Chunk |
| Testing 有结果，Search 无结果 | Search 保存阈值、doc_ids、metadata filter |
| 结果正确，摘要却引用不同段落 | 两条独立召回的 query、doc_ids、KG/父块与数量差异 |
| 已开增强却没有效果 | 配置字段是否实际被该入口读取，跨语言键名是否一致 |
| SSE 有答案无来源 | summary/引用配置、检索结果 |
| 分享页失败 | 分享 Token、Search 状态、知识库权限 |

## 11. 本册检查点

- 能区分 Search App 与 Dataset Testing。
- 能解释 Search 配置如何复用 Dealer。
- 能按 search_id 串起保存配置、SSE 和检索日志。
- 能区分 Search 与 Chat 的状态模型。
