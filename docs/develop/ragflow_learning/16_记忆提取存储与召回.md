# 第十六册：记忆的提取、存储与召回

Memory 不是 Conversation 的别名。Conversation 保存某次对话历史；Memory 从对话中抽取可跨会话复用的信息，并建立独立全文与向量索引。

## 1. 前端页面

```text
web/src/pages/memories/        Memory 列表、创建、重命名、删除
web/src/pages/memory/
  ├─ memory-setting/           模型、类型、容量、Prompt、权限
  └─ memory-message/           原始消息和抽取结果
```

请求封装：`web/src/services/memory-service.ts`。

## 2. Memory 类型

`MemoryType` 使用 bit flags：

| 类型 | 值 | 含义 |
|---|---:|---|
| `raw` | 1 | 原始 user input + agent response |
| `semantic` | 2 | 相对稳定的事实/语义知识 |
| `episodic` | 4 | 发生过的事件与经历 |
| `procedural` | 8 | 偏好、步骤和行为方式 |

可组合，例如 `5` 表示 raw + episodic。页面传字符串列表，`MemoryService` 转为整数位图。

## 3. 两类存储

```text
MySQL Memory
  → 名称、权限、模型、类型、容量、Prompt 等配置

settings.msgStoreConn
  → 原始消息、抽取消息、content_embed、有效期、状态
```

消息索引名：

```text
memory_<tenant_id>
```

`memory_id` 作为索引内部的 Memory 分区。设置 `ES_INDEX_PREFIX` 时，消息索引名由 `memory/services/messages.py::index_name` 生成 `memory_<prefix>_<tenant_id>`。Memory 消息不写入普通 `ragflow_<tenant>` Chunk 索引。`storage_type` 字段允许表达 table/graph，但本册核查到的写入与召回链路使用消息表/索引，不能据此推断已实现 Graph Memory。

## 4. `Memory` 模型

| 字段 | 含义 |
|---|---|
| `tenant_id` | 所有者 |
| `memory_type` | 类型位图 |
| `storage_type` | `table|graph` |
| `embd_id/tenant_embd_id` | Embedding 模型 |
| `llm_id/tenant_llm_id` | 抽取用 Chat 模型 |
| `permissions` | `me|team` |
| `memory_size` | 最大容量，按内容和向量估算 |
| `forgetting_policy` | 当前支持 FIFO |
| `temperature` | 抽取模型温度 |
| `system_prompt/user_prompt` | 记忆抽取 Prompt |

## 5. CRUD 接口

```text
POST   /memories
GET    /memories
GET    /memories/<memory_id>/config
PUT    /memories/<memory_id>
DELETE /memories/<memory_id>
```

创建必须提供：`name`、`memory_type`、`embd_id`、`llm_id`。创建时解析租户模型标识、生成默认 system prompt，并写 MySQL Memory；消息索引在首条消息 `embed_and_save()` 时按实际向量维度创建。

已有消息时，不允许随意切换 `embd_id` 或 `memory_type`，因为现有向量和抽取记录与旧配置绑定。

## 6. Memory 权限

可访问条件：

```text
memory.tenant_id == current_user.id
OR
memory.permissions == team
AND current_user 属于该 tenant
```

不可访问的 Memory 对外按 not found 处理，减少资源存在性泄露。

## 7. 添加一轮对话

```text
POST /messages
body:
  memory_id[]
  agent_id
  session_id
  user_input
  agent_response
```

JWT/Session 用户不能伪造 `user_id`；API Token 调用可提供外部 subject ID。日志只记录 subject 来源，不记录实际终端用户 ID。

## 8. 同步与异步提取链路

核心函数位于 `api/db/joint_services/memory_message_service.py`。

```text
一轮对话
  → 生成 raw message_id（Redis 自增）
  → 保存 raw 内容和 Embedding
  → 创建 MySQL Task(task_type=memory)
  → Redis 投递
  → Worker Memory 分支
  → LLM 按 semantic/episodic/procedural 抽取 JSON
  → 每条派生记忆关联 source_id=raw_message_id
  → Embedding
  → msgStoreConn.insert
  → Task progress 完成
```

这张图对应 `/messages` 使用的 `queue_save_to_memory_task()`：同步完成 RAW 的 Embedding 与消息写入后，才保存 Task 并投递 Redis。Task 的 `doc_id` 在此复用为 `memory_id`，`digest` 保存 RAW `message_id`，不表示文件内容摘要。只启用 raw 时仍创建并投递 Task；Worker 的 `save_extracted_to_memory_only()` 会直接完成，不调用 LLM。

因此“添加成功”不等于派生记忆完成，RAW、MySQL Task、Redis 投递也没有统一事务。Redis 投递失败时 RAW 与 Task 可能已保存；抽取返回空数组则可正常完成。另一个 `save_to_memory()` 函数会在同一次调用中抽取、保存 RAW 与派生消息，它不是当前 `/messages` 的入队入口。

## 9. 消息结构

| 字段 | 作用 |
|---|---|
| `message_id` | Redis 全局自增 ID |
| `message_type` | raw/semantic/episodic/procedural |
| `source_id` | 派生记录指向 raw message_id |
| `memory_id` | 所属 Memory |
| `user_id` | 终端主体 |
| `agent_id/session_id` | 来源运行 |
| `content` | 原文或提取内容 |
| `content_embed` | 向量 |
| `valid_at/invalid_at` | 有效时间范围 |
| `forget_at` | 遗忘时间 |
| `status` | 是否参与默认召回 |

Doc Store `_id` 形式为 `<memory_id>_<message_id>`。

## 10. LLM 抽取

`extract_by_llm()`：

1. 根据 Memory 类型组装 system prompt；
2. 把 user input、agent response 和当前时间写入 user prompt；
3. 调用租户 Chat 模型；
4. 解析结构化 JSON；
5. 标准化 valid/invalid 时间；
6. 生成不同 message_type 的派生记录。

抽取错误可能表现为模型调用失败或 JSON 修复失败；没有产生派生记忆是一个允许成功的结果。原始 raw 消息可以已经保存，而抽取 Task 失败。

## 11. Embedding 与容量

`embed_and_save()`：

```text
解析 Embedding 模型
  → 批量 encode(content)
  → 创建 memory index/mapping
  → 估算新消息大小
  → 检查 memory_size
  → FIFO 选择旧消息删除
  → insert_message
  → 更新 Redis 容量缓存
```

Embedding 优先按 `tenant_embd_id` 解析租户模型，失效或缺失时回退到 `embd_id`；抽取模型对 `tenant_llm_id/llm_id` 使用相同规则。容量按 `calculate_message_size()` 对文本和向量的 Python 对象大小估算，并非对象存储实际占用；FIFO 优先删除已遗忘消息，再按 `valid_at` 从旧到新选取。容量缓存 key 为 `memory_<memory_id>`。Redis 缓存丢失时可从 msg store 重新计算。

## 12. 召回

```text
GET /messages/search
```

参数：

- `memory_id`：一个或多个；
- `query`；
- `similarity_threshold`；
- `keywords_similarity_weight`；
- `top_n`；
- 可选 `agent_id/session_id/user_id`。

`query_message()` 同时构建：

```text
MsgTextQuery       全文匹配
MatchDense         向量匹配
FusionExpr         weighted_sum
```

默认语义召回补充 `status=1`，后端默认隐藏已设置 `forget_at` 的消息；`valid_at/invalid_at` 是存储字段，当前此路径没有通用的“按当前时刻校验有效期”过滤。检索向量在 `query_message()` 中按首个 Memory 的 `embd_id` 生成，因此多 Memory 应使用一致的 Embedding 空间；Agent 的 Retrieval 会校验模型一致性，通用 `/messages/search` 当前未做同样的跨 Memory 校验。

## 13. 最近消息与语义召回

```text
GET /messages
```

按 agent/session 读取最近消息，按 `valid_at` 倒序，默认隐藏已遗忘消息；此路径没有像语义召回一样主动补充 `status=1`，也没有限定只返回 raw，不能直接等同于 Conversation 的原始消息历史。

```text
GET /messages/search
```

按问题相关性召回长期记忆。Agent 可以同时使用两者：最近对话保证连续性，语义记忆提供跨会话信息。

## 14. 消息管理

```text
GET    /memories/<id>                         列出 raw 及其 extract
GET    /messages/<memory_id>:<message_id>/content
PUT    /messages/<memory_id>:<message_id>     开关 status
DELETE /messages/<memory_id>:<message_id>     forget
```

列表先查 raw，再按 `source_id` 批量加载派生消息，页面因此能展开查看一轮对话抽取出的多种记忆。管理列表使用 `hide_forgotten=False`，已遗忘消息仍可展示。`DELETE /messages/...` 当前只写 `forget_at`，不物理删除、不立即释放容量，也不按 `source_id` 连带遗忘派生消息；状态开关也只作用于指定消息。

## 15. 删除 Memory

当前 `memory_api_service.delete_memory()` 的顺序是：验证访问权限 → 删除 MySQL Memory → 索引存在时按 `memory_id` 删除消息。它没有调用 `delete_index()` 删除整个索引，也没有在此清理 Redis 容量缓存、未完成 Task 或 Agent DSL 中的引用；这些属于排查残留状态时需要另外核对的边界。

MySQL 删除与消息删除没有统一事务。删除后的 Memory Task 再执行时，会因找不到 Memory 而失败；不能把删除接口成功理解为所有关联状态都已回收。

## 16. Agent 集成

当前 Python Agent 的明确入口是 `agent/component/message.py::Message._save_to_memory()` 和 `agent/tools/retrieval.py::Retrieval._retrieve_memory()`：Message 根据 `memory_ids` 保存本轮 query/answer，Retrieval 选择 `retrieval_from=memory` 后进行语义召回。没有独立 Python `Memory` 组件可仅凭名称创建。

Message 写入的 `agent_id` 是 Canvas ID，`session_id` 来自 Canvas `task_id`；`user_id` 可由配置和变量引用获得。Retrieval 只在配置了 `user_id` 时加主体过滤，并不会自动追加 agent/session 隔离。组件直调 joint service，与 REST 的 `_require_memory_access()` 校验路径不同，不能将 REST 权限校验直接套用到所有组件调用。Memory 的 `agent_id` 是消息来源字段，不等于 Memory 只能被一个 Agent 使用。

## 17. 调试断点

```text
memory_api.add_message
  → memory_api_service.add_message
  → queue_save_to_memory_task
  → embed_and_save(raw)
  → Redis Task
  → TaskHandler memory branch
  → save_extracted_to_memory_only
  → extract_by_llm
  → embed_and_save(extracted)
  → MessageService.insert_message
```

召回断点：

```text
memory_api.search_message
  → query_message
  → MsgTextQuery/get_vector/FusionExpr
  → MessageService.search_message
  → settings.msgStoreConn.search
```

## 18. 常见故障

| 现象 | 检查 |
|---|---|
| raw 有、extract 无 | memory Task、LLM、Prompt、JSON |
| 搜不到刚写入内容 | status、Embedding、refresh、filter |
| 容量很快满 | 向量维度、memory_size、消息长度 |
| 改不了 Embedding | Memory 非空保护 |
| 其他用户看不到 team Memory | UserTenant、permissions |
| 重启后 ID/容量异常 | Redis 初始化与 msg store 重算 |

## 19. 本册检查点

- 能区分 Conversation、raw memory 和提取记忆。
- 能解释四种类型位图和 source_id。
- 能说明消息为何保存在 msgStoreConn 而非 MySQL。
- 能跟踪 Memory Task 的异步抽取。
- 能解释全文+向量融合召回和 FIFO 遗忘。
