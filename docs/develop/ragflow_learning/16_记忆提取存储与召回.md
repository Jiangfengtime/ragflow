# 第十六册：记忆的提取、存储与召回

Memory 不是 Conversation 的别名。Conversation 保存某次对话历史；Memory 从对话中抽取可跨会话复用的信息，并建立独立全文与向量索引。

## 1. 前端页面

```text
web/src/pages/memories/        Memory 列表、创建、重命名、删除
web/src/pages/memory/
  ├─ memory-setting/           模型、类型、容量、Prompt、权限
  └─ memory-message/           原始消息和抽取结果
```

请求封装：`web/src/services/memory-service.ts`。

## 2. Memory 类型

`MemoryType` 使用 bit flags：

| 类型 | 值 | 含义 |
|---|---:|---|
| `raw` | 1 | 原始 user input + agent response |
| `semantic` | 2 | 相对稳定的事实/语义知识 |
| `episodic` | 4 | 发生过的事件与经历 |
| `procedural` | 8 | 偏好、步骤和行为方式 |

可组合，例如 `5` 表示 raw + episodic。页面传字符串列表，`MemoryService` 转为整数位图。

## 3. 两类存储

```text
MySQL Memory
  → 名称、权限、模型、类型、容量、Prompt 等配置

settings.msgStoreConn
  → 原始消息、抽取消息、content_embed、有效期、状态
```

消息索引名：

```text
memory_<tenant_id>
```

`memory_id` 作为索引内部的 Memory 分区。Memory 消息不写入普通 `ragflow_<tenant>` Chunk 索引。

## 4. `Memory` 模型

| 字段 | 含义 |
|---|---|
| `tenant_id` | 所有者 |
| `memory_type` | 类型位图 |
| `storage_type` | `table|graph` |
| `embd_id/tenant_embd_id` | Embedding 模型 |
| `llm_id/tenant_llm_id` | 抽取用 Chat 模型 |
| `permissions` | `me|team` |
| `memory_size` | 最大容量，按内容和向量估算 |
| `forgetting_policy` | 当前支持 FIFO |
| `temperature` | 抽取模型温度 |
| `system_prompt/user_prompt` | 记忆抽取 Prompt |

## 5. CRUD 接口

```text
POST   /memories
GET    /memories
GET    /memories/<memory_id>/config
PUT    /memories/<memory_id>
DELETE /memories/<memory_id>
```

创建必须提供：`name`、`memory_type`、`embd_id`、`llm_id`。创建时自动生成默认 system prompt。

已有消息时，不允许随意切换 `embd_id` 或 `memory_type`，因为现有向量和抽取记录与旧配置绑定。

## 6. Memory 权限

可访问条件：

```text
memory.tenant_id == current_user.id
OR
memory.permissions == team
AND current_user 属于该 tenant
```

不可访问的 Memory 对外按 not found 处理，减少资源存在性泄露。

## 7. 添加一轮对话

```text
POST /messages
body:
  memory_id[]
  agent_id
  session_id
  user_input
  agent_response
```

JWT/Session 用户不能伪造 `user_id`；API Token 调用可提供外部 subject ID。日志只记录 subject 来源，不记录实际终端用户 ID。

## 8. 同步与异步提取链路

核心函数位于 `api/db/joint_services/memory_message_service.py`。

```text
一轮对话
  → 生成 raw message_id（Redis 自增）
  → 保存 raw 内容和 Embedding
  → 创建 MySQL Task(task_type=memory)
  → Redis 投递
  → Worker Memory 分支
  → LLM 按 semantic/episodic/procedural 抽取 JSON
  → 每条派生记忆关联 source_id=raw_message_id
  → Embedding
  → msgStoreConn.insert
  → Task progress 完成
```

只启用 raw 时无需 LLM 抽取。

## 9. 消息结构

| 字段 | 作用 |
|---|---|
| `message_id` | Redis 全局自增 ID |
| `message_type` | raw/semantic/episodic/procedural |
| `source_id` | 派生记录指向 raw message_id |
| `memory_id` | 所属 Memory |
| `user_id` | 终端主体 |
| `agent_id/session_id` | 来源运行 |
| `content` | 原文或提取内容 |
| `content_embed` | 向量 |
| `valid_at/invalid_at` | 有效时间范围 |
| `forget_at` | 遗忘时间 |
| `status` | 是否参与默认召回 |

Doc Store `_id` 形式为 `<memory_id>_<message_id>`。

## 10. LLM 抽取

`extract_by_llm()`：

1. 根据 Memory 类型组装 system prompt；
2. 把 user input、agent response 和当前时间写入 user prompt；
3. 调用租户 Chat 模型；
4. 解析结构化 JSON；
5. 标准化 valid/invalid 时间；
6. 生成不同 message_type 的派生记录。

抽取错误可能表现为模型调用失败、JSON 修复失败或没有产生任何记忆。原始 raw 消息可以已经保存，而抽取 Task 失败。

## 11. Embedding 与容量

`embed_and_save()`：

```text
解析 Embedding 模型
  → 批量 encode(content)
  → 创建 memory index/mapping
  → 估算新消息大小
  → 检查 memory_size
  → FIFO 选择旧消息删除
  → insert_message
  → 更新 Redis 容量缓存
```

容量缓存 key 为 `memory_<memory_id>`。Redis 缓存丢失时可从 msg store 重新计算。

## 12. 召回

```text
GET /messages/search
```

参数：

- `memory_id`：一个或多个；
- `query`；
- `similarity_threshold`；
- `keywords_similarity_weight`；
- `top_n`；
- 可选 `agent_id/session_id/user_id`。

`query_message()` 同时构建：

```text
MsgTextQuery       全文匹配
MatchDense         向量匹配
FusionExpr         weighted_sum
```

默认只召回 `status=1` 的有效消息。

## 13. 最近消息与语义召回

```text
GET /messages
```

按 agent/session 读取最近消息，用于短期上下文。

```text
GET /messages/search
```

按问题相关性召回长期记忆。Agent 可以同时使用两者：最近对话保证连续性，语义记忆提供跨会话信息。

## 14. 消息管理

```text
GET    /memories/<id>                         列出 raw 及其 extract
GET    /messages/<memory_id>:<message_id>/content
PUT    /messages/<memory_id>:<message_id>     开关 status
DELETE /messages/<memory_id>:<message_id>     forget
```

列表先查 raw，再按 `source_id` 批量加载派生消息，页面因此能展开查看一轮对话抽取出的多种记忆。

## 15. 删除 Memory

删除时必须处理：

- MySQL Memory；
- msg store 中该 memory_id 的索引/分区；
- Redis 容量缓存；
- 未完成的 memory Task；
- Agent DSL 中对该 Memory 的引用。

不能只删 MySQL 行，否则消息索引会成为孤儿数据。

## 16. Agent 集成

Agent 中的 Memory 组件或运行配置决定：

- 哪些 Memory 可写；
- 一轮完成后何时写入；
- 按 agent/session/user 如何隔离；
- 下一轮读取最近消息还是语义召回；
- 写入失败是否影响 Agent 主回答。

Memory 的 `agent_id` 是消息来源字段，不等于 Memory 只能被一个 Agent 使用。

## 17. 调试断点

```text
memory_api.add_message
  → memory_api_service.add_message
  → queue_save_to_memory_task
  → embed_and_save(raw)
  → Redis Task
  → TaskHandler memory branch
  → save_extracted_to_memory_only
  → extract_by_llm
  → embed_and_save(extracted)
  → MessageService.insert_message
```

召回断点：

```text
memory_api.search_message
  → query_message
  → MsgTextQuery/get_vector/FusionExpr
  → MessageService.search_message
  → settings.msgStoreConn.search
```

## 18. 常见故障

| 现象 | 检查 |
|---|---|
| raw 有、extract 无 | memory Task、LLM、Prompt、JSON |
| 搜不到刚写入内容 | status、Embedding、refresh、filter |
| 容量很快满 | 向量维度、memory_size、消息长度 |
| 改不了 Embedding | Memory 非空保护 |
| 其他用户看不到 team Memory | UserTenant、permissions |
| 重启后 ID/容量异常 | Redis 初始化与 msg store 重算 |

## 19. 本册检查点

- 能区分 Conversation、raw memory 和提取记忆。
- 能解释四种类型位图和 source_id。
- 能说明消息为何保存在 msgStoreConn 而非 MySQL。
- 能跟踪 Memory Task 的异步抽取。
- 能解释全文+向量融合召回和 FIFO 遗忘。
