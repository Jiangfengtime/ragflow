# 第七册：状态、一致性与故障恢复

RAGFlow 的一次文档解析跨越 MySQL、MinIO、Redis 和 Doc Store。它不是一个跨四种存储的数据库事务，因此理解“事实源、派生数据、消息确认、幂等与补偿”比记住某个函数更重要。

## 1. 四类存储的事实边界

| 存储 | 保存什么 | 是否事实源 | 典型恢复方式 |
|---|---|---|---|
| MySQL | 用户、租户、知识库、文档、Task、配置、进度 | 业务元数据与任务状态的事实源 | 数据库备份/迁移 |
| MinIO | 原文件、缩略图、Chunk 图片和附件 | 文件内容事实源 | 对象存储备份 |
| Redis | Stream 消息、Pending、锁、计数器、取消标记和缓存 | 运行协调，不是最终业务事实源 | 重发任务或重建临时状态 |
| Elasticsearch 等 Doc Store | Chunk 文本、元数据、向量、检索结构 | 可重建的检索派生数据 | 从 MySQL + MinIO 重新解析和索引 |

“可重建”不等于“不用备份”。重建大型知识库可能耗时并再次消耗 OCR、Embedding 或外部模型费用。

## 2. 文档与任务不是同一个状态机

### 2.1 `Document.run`

`common/constants.py:TaskStatus` 定义文档展示状态：

| 值 | 名称 | 含义 |
|---|---|---|
| `0` | `UNSTART` | 已上传，尚未开始解析 |
| `1` | `RUNNING` | 已排队或正在处理 |
| `2` | `CANCEL` | 已请求取消 |
| `3` | `DONE` | 文档任务已完成 |
| `4` | `FAIL` | 关键阶段失败 |
| `5` | `SCHEDULE` | 调度状态 |

`Document.run=1` 不能证明 Worker 正在占用 CPU。它也可能处于队列等待、模型限流、重试或进度尚未汇总的阶段。

### 2.2 `Task.progress`

一个 Document 可以拆成多个 Task。`Task` 保存页/行范围、进度、错误信息、digest 和已经写入的 `chunk_ids`。

常见约定：

- `0 <= progress < 1`：排队或处理中；
- `progress == 1`：完成；
- 负值：失败；
- `progress_msg`：当前阶段或错误说明；
- `chunk_ids`：该 Task 已成功建立索引的 Chunk，用于恢复和清理。

文档状态由多个 Task 汇总，因此排查时不能只看 `document.run`。

### 2.3 Redis 消息状态

Redis Stream 的状态又是第三层：

```text
XADD
  → 未分配的新消息
XREADGROUP
  → 当前消费者已领取，进入 Pending Entries List
XACK
  → 当前消费者组确认完成
```

Pending 只说明“消息被领过但尚未确认”，不说明 Task 成功或失败。最终业务状态仍要看 MySQL。

## 3. 为什么一个文档有多个 Task

`api/db/services/task_service.py:queue_tasks` 根据文件类型拆分任务：

- PDF 通常按页范围拆分；
- `paper` 可使用不同默认页数；
- MinerU、`one`、知识图谱或需要目录抽取的文档可不拆页；
- 表格使用 `from_page/to_page` 表示行范围；
- 其他类型通常只有一个 Task。

拆分带来并发和失败隔离，但也引入文档级汇总：所有分页 Task 完成后，最后一个任务才执行某些文档级收尾动作。

## 4. 创建任务时的写入顺序

标准链路的关键顺序：

```text
1. 读取 Document 和解析配置
2. 计算 Task 列表与 digest
3. 处理旧 Task/旧 Chunk 的复用或清理
4. MySQL 批量插入新 Task
5. DocumentService.begin2parse
6. 初始化文档级 Redis 计数器
7. 将未完成 Task 逐条 XADD 到 Redis Stream
```

先写 MySQL，再投递 Redis，避免 Worker 拿到 `task_id` 后数据库里还不存在该任务。

但这不是分布式事务：如果 MySQL 成功而 Redis 投递失败，MySQL 中可能保留排队状态。代码会清理计数器并抛出异常，运维上仍应检查并重新触发解析。

## 5. Task 消息为什么只放轻量字段

Redis 消息包含任务标识和页范围等必要信息，Worker 随后通过 Task Service 从 MySQL 加载文档、知识库、模型和解析配置。

优点：

- 配置的事实源仍在数据库；
- 消息体更小；
- 不必在队列里复制完整文档配置；
- 能在领取任务后统一校验 Document 是否仍存在或已取消。

代价是 Worker 依赖 MySQL 可用，且“消息存在但 Task 被删除”必须被识别为无效任务。

## 6. 消费者组与至少一次处理

`REDIS_CONN.queue_consumer()` 使用 `XREADGROUP`：

- `msg_id='>'` 读取尚未分配的新消息；
- 消费组不存在时创建；
- 一次最多领取一条；
- 没有新消息时返回 `None`，这是正常轮询，不是异常；
- 领取后进入 Pending，调用 `RedisMsg.ack()` 才 `XACK`。

Worker 崩溃可能导致同一任务重新处理，因此业务必须按“至少一次”而不是“严格一次”设计。严格一次通常需要跨数据库、队列和 ES 的全局事务，系统并没有这样的事务。

## 7. 幂等依赖哪些机制

### 7.1 Task digest

`queue_tasks()` 根据文档 ID、页范围和解析配置计算 digest。重新解析时，如果旧 Task 已完成且 digest 匹配，可以复用旧 Chunk，避免重复解析和 Embedding。

修改会影响 Chunk 的配置后，digest 应发生变化，旧 Chunk 不应被误复用。

### 7.2 稳定 Chunk ID

标准切片路径使用文档与内容生成稳定 ID。相同文档、相同内容再次写入时，Doc Store 可覆盖同一 `_id`，降低重复记录概率。

稳定 ID 不能代替旧数据清理：切片边界改变后会产生新 ID，旧 ID 若不删除仍会成为脏数据。

### 7.3 `Task.chunk_ids` 检查点

`ChunkService.insert_chunks()` 分批写 Doc Store，并周期性把已写入 ID 保存到 `Task.chunk_ids`。Worker 中途崩溃后，这些 ID 能用于：

- 判断已经写入了什么；
- 重跑前删除旧结果；
- 插入状态无法持久化时回滚当前批次。

它是跨存储补偿的检查点，不只是展示字段。

## 8. Chunk 写入的部分失败

Bulk API 返回 HTTP 200 不代表每个 item 都成功。正确判断至少包括：

1. 响应 HTTP status；
2. `errors` 是否为 `false`；
3. 每个 `items[*].index` 是否有错误；
4. 成功数量是否符合预期。

当前插入路径分批处理并保存检查点。如果 ES 写成功、随后 MySQL 更新 `chunk_ids` 失败，代码会尝试删除刚写入的 Chunk，避免无法追踪的孤儿索引。

## 9. 文档级进度汇总

`DocumentService.update_progress()` 周期性读取未完成文档，查询其所有 Task 并同步：

- 文档总进度；
- 汇总消息；
- 完成、失败或取消状态；
- 处理耗时；
- Chunk/Token 等统计。

因此页面进度可能落后于单个 Task 的实时值。Debug 时以 Task 为细粒度证据，以 Document 为汇总状态。

## 10. 取消语义

取消不是杀死线程的瞬时操作，而是协作式状态变化：

1. 接口把文档/任务标记为取消；
2. 设置 Worker 可检测的取消状态；
3. Worker 在阶段边界检查；
4. 停止后续解析、Embedding 或写入；
5. 清理已经写入的 Chunk/图片和临时状态；
6. 更新 MySQL 状态并确认消息。

如果底层 OCR、外部模型或同步解析函数不响应取消，状态更新与实际停止之间可能有延迟。

## 11. 重新解析语义

重新解析不是简单追加：

```text
读取旧 Task
  → 按 digest 尝试复用已完成 Chunk
  → 收集不能复用的旧 chunk_ids
  → 从 Doc Store 删除旧 Chunk
  → 删除旧 Task 记录
  → 创建新 Task
  → 更新 Document.chunk_num
  → 投递未完成 Task
```

如果解析配置、Embedding 模型或原文件内容改变，应特别验证：

- 旧向量字段是否清理；
- 新向量维度是否与知识库配置一致；
- `Document.chunk_num/token_num` 是否与 ES 实际数量一致；
- 是否存在复用不应复用的旧 Task。

## 12. 删除语义

删除 Document 涉及多个系统：

1. 验证文档所属知识库和用户权限；
2. 取消运行中的 Task；
3. 删除 Doc Store 中 `doc_id` 对应的 Chunk；
4. 删除 Task；
5. 删除 File2Document 等关系；
6. 按业务语义处理 File/MinIO 对象；
7. 更新 Knowledgebase 统计。

实际代码路径可能因文件来源和是否被多个对象引用而不同，因此不要在数据库里直接 `DELETE document`。直接删 MySQL 行很容易留下 ES Chunk 和 MinIO 对象。

## 13. `_prune_deleted_chunks` 是什么

`rag/nlp/search.py:_prune_deleted_chunks` 是检索侧安全网：

1. 从 ES 候选读取 `doc_id`；
2. 到 MySQL 查询这些 Document 是否仍存在；
3. 丢弃父文档已不存在的 Chunk。

它避免删除不完整时向用户召回脏数据，但不是主删除机制。持续出现被过滤的孤儿 Chunk 表示删除链路或历史数据需要修复。

## 14. 常见不一致场景

| 场景 | 表现 | 判断方法 | 恢复建议 |
|---|---|---|---|
| MySQL 有 Task，Redis 无消息 | 文档长期 queued | 查 Task、Stream、日志 | 重新触发解析或安全重投 |
| Redis 有消息，MySQL 无 Task | Worker 领到后无法加载 | 查消息 task_id | 确认无效后 ACK/清理消息 |
| ES 有 Chunk，MySQL 无 Document | 检索安全网过滤 | 按 doc_id 查两边 | 删除孤儿 Chunk |
| Document DONE，ES 无 Chunk | 查询为空 | 查 Task.chunk_ids 与 ES | 重解析并查 ES 错误 |
| MinIO 对象丢失 | Worker 读取原文失败 | 用 kb_id/location 查对象 | 从备份恢复或重新上传 |
| 多个 Task 一直差一个完成 | 文档进度停住 | 查所有 Task 和 Redis Pending | 恢复 Pending 或重跑失败页 |
| Embedding 维度变化 | ES 查询/写入报错 | 查 `q_{dim}_vec` | 重建相应知识库索引 |

## 15. 一致性核对方法

对一个 `doc_id`，依次核对：

```sql
SELECT id, kb_id, location, run, progress, chunk_num, token_num
FROM document WHERE id = '<doc_id>';

SELECT id, doc_id, from_page, to_page, progress, progress_msg, chunk_ids
FROM task WHERE doc_id = '<doc_id>' ORDER BY from_page;

SELECT file_id, document_id
FROM file2document WHERE document_id = '<doc_id>';
```

然后检查：

- MinIO：bucket=`kb_id`、object=`location` 是否存在；
- Redis：相应优先级 Stream 中是否有消息或 Pending；
- ES：按 `doc_id` 统计 Chunk 数、抽查 `q_*_vec` 字段；
- 日志：按 `doc_id/task_id` 串起阶段。

不要在共享环境把真实 API Key、文档正文或完整向量复制进工单。

## 16. 故障注入学习法

仅在本地测试数据上进行：

| 断点/停止位置 | 预期现象 | 要验证的机制 |
|---|---|---|
| Task 写 MySQL 后、XADD 前 | 有 Task、无消息 | 非分布式事务窗口 |
| XREADGROUP 后、XACK 前 | Pending 保留 | 消息恢复 |
| ES Bulk 后、chunk_ids 更新前 | 可能触发回滚 | 跨存储补偿 |
| 一个分页 Task 完成后 | 其他 Task 继续 | 文档一对多 Task |
| Document 删除后 | ES 不应召回 | 主清理 + prune 安全网 |

## 17. 生产恢复原则

- 先做只读核对，再修改状态。
- 优先调用正式 API 或 Service，不直接手改多张表。
- 重投前确认原任务是否仍可能运行，避免并发双写。
- 清理 ES 前记录 `tenant_id/kb_id/doc_id/chunk_ids`。
- 重要知识库重建前确认原文件和模型凭据可用。
- 恢复后同时验证 MySQL 状态、ES 数量和真实查询结果。
